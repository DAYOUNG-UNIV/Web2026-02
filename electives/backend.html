백엔드: 요청을 받아 응답하는 서버 만들기

브라우저 혼자서는 할 수 없는 일이 생기면 서버가 필요합니다. 이 모듈에서는 서버가 필요한 순간을 가려내고, Node.js와 Express 5로 메모 분류 API를 끝까지 만들어 봅니다. 실습은 모두 브라우저 안의 연습용 서버에서 돌아갑니다. 마지막에는 우리 팀에 서버가 정말 필요한지 결정표로 답합니다.

  • 예상 시간 읽기 20~30분 · 실습 30분
  • 먼저 볼 것 10주차 터미널·요청과 응답, 11주차 fetch와 '서버가 필요한 순간' (교안 지도에서 엽니다)
  • 기본 도구 ChatGPT Edu(기본) · 에이전트(Codex 또는 Claude Code)
  • AI 등급 AI ALLOWED

이 모듈이 맞는 프로젝트

잘 맞는 경우
  • 여러 사람이 같은 데이터를 보고 바꿉니다. 예: 팀원 1이 올린 메모를 팀원 2가 분류합니다.
  • "누가 했는지"를 서버가 확인해야 합니다. 예: 내 메모는 나만 지울 수 있습니다.
  • 비밀 키가 필요한 외부 API를 부릅니다. 키는 브라우저에 둘 수 없으므로 중간에 서버가 섭니다.
  • BaaS의 표 구조로는 풀기 어려운 자유로운 처리가 있습니다. 예: 여러 단계를 거쳐 계산한 뒤 저장합니다.
과한 경우
  • 데이터가 한 사람의 브라우저 안에만 있어도 됩니다. 11주차의 localStorage로 충분합니다.
  • "여럿이 같이 쓰는 표" 정도입니다. 서버리스·BaaS(선택 모듈 3)가 더 빠르고 운영 부담이 적습니다.
  • 서버를 켜 두고 돌볼 사람이 팀에 없습니다. 서버는 만드는 것보다 켜 두는 일이 더 깁니다.
먼저 할 것
11주차의 '서버가 필요한 순간' 판별표에 팀이 함께 답합니다. 터미널에서 node -v가 22 이상이면 준비는 끝입니다. 선택 모듈 3(서버리스)을 먼저 읽고 둘을 나란히 비교하기를 권합니다. 이 수업의 팀 프로젝트에서는 서버리스·BaaS를 먼저 검토합니다.

진행 상황을 표시하며 따라가세요. 표시는 이 브라우저에만 저장됩니다.

서버가 필요한 순간

브라우저는 한 사람의 화면입니다. 다른 사람과 데이터를 나누거나, 비밀을 지키거나, 누가 했는지 확인하려면 모두가 접근할 수 있는 한 곳이 필요합니다. 그곳이 서버입니다.

10주차 '로컬 서버와 요청·응답 읽기'에서 본 기준 한 줄을 다시 씁니다. 서버가 요청마다 코드를 실행하는가. GitHub Pages는 파일을 그대로 돌려줄 뿐 코드를 실행하지 않습니다(정적 호스팅). 이 모듈의 서버는 요청이 올 때마다 코드를 실행해 응답을 만듭니다(동적). 어느 쪽이 필요한지는 다음 표로 가립니다.

서버가 필요한지 가리는 질문 — 메모 앱으로 답해 보기
질문"예"라면메모 앱의 예
여러 사람이 같은 데이터를 보나요?데이터가 한 곳에 있어야 합니다. 서버 또는 BaaS.팀원 1이 올린 메모를 팀원 2가 봅니다.
여러 기기에서 이어서 쓰나요?브라우저 저장소는 기기마다 따로입니다. 서버 또는 BaaS.노트북에서 쓴 메모를 폰에서 봅니다.
누가 했는지 확인해야 하나요?로그인과 권한은 서버가 확인합니다.내 메모는 나만 지웁니다.
비밀 키가 필요한 API를 부르나요?키는 서버에만 둡니다. 브라우저 코드는 누구나 읽습니다.메모를 AI로 요약합니다(선택 모듈 4).

언제 직접 만드는 서버가 과한가

"예"가 하나라도 있어도 길은 세 갈래입니다. 이 수업에서는 가운데 길을 먼저 검토합니다. 직접 만드는 서버는 자유롭지만, 켜 두고 돌보는 일까지 팀이 맡게 됩니다.

데이터를 두는 세 가지 길
길언제새로 배울 것운영 부담
localStorage (11주차)한 사람, 한 브라우저없음없음
서버리스 · BaaS (선택 모듈 3)여럿이 같이 쓰는 표, 로그인, 실시간콘솔 설정, 키 구분, 접근 규칙(RLS)낮음. 무료 프로젝트는 쉬면 멈추므로 시연 전에 깨웁니다.
직접 만드는 서버 (이 모듈)자유로운 처리, 비밀 키 프록시, 표로 안 풀리는 구조라우트, 검증, 저장, CORS, 배포높음. 켜 두는 사람, 재시작, 데이터 백업이 필요합니다.

이 모듈을 읽고 "우리는 BaaS로 충분하다"고 결정해도 됩니다. 결정표(08)에 그 이유를 적으면 그것이 이 모듈의 결과물입니다. 서버를 만드는 것이 목표가 아니라, 필요한지 판단하는 것이 목표입니다.

핵심 개념 네 가지

요청이 들어와 응답이 나가기까지, 입력을 믿지 않는 법, 데이터를 어디에 남길지, 그리고 브라우저와 서버를 잇는 규칙입니다. 개념마다 바로 실행할 수 있는 최소 예제가 붙어 있습니다.

요청이 들어와 응답이 나가기까지

10주차 Network 탭에서 본 한 줄, 예를 들어 GET /api/notes 200은 서버 안에서 네 단계를 지납니다.

  1. 요청 도착메서드, 경로, 쿼리, 본문(JSON)이 함께 옵니다.
  2. 미들웨어express.json()이 본문을 객체로 바꾸고, cors()가 허용 헤더를 붙입니다.
  3. 라우트 핸들러경로와 메서드가 맞는 함수 하나가 실행됩니다.
  4. 응답상태 코드와 JSON을 돌려주고 끝냅니다. 한 요청에 응답은 한 번입니다.

Express 5로 쓴 가장 작은 메모 API입니다. 파일 하나, 라우트 셋, 오류 처리 하나입니다.

import express from 'express';
import cors from 'cors';

const app = express();
app.use(cors());            // 다른 출처(예: GitHub Pages)에서 불러도 됨
app.use(express.json());    // JSON 본문을 req.body로

let notes = [{ id: 1, title: '첫 메모', category: '수업' }];

app.get('/api/notes', (req, res) => res.json(notes));

app.post('/api/notes', (req, res) => {
  const note = { id: Date.now(), title: req.body.title, category: req.body.category };
  notes.push(note);
  res.status(201).json(note);           // 만들었으니 201
});

app.get('/api/notes/:id', (req, res) => {
  const note = notes.find((n) => n.id === Number(req.params.id));
  if (!note) return res.status(404).json({ error: 'Not Found' });
  res.json(note);
});

// 오류 미들웨어는 마지막에, 인자 네 개
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: 'Internal Server Error' });
});

app.listen(3000, () => console.log('http://localhost:3000'));

이 파일은 package.json에 "type": "module"이 있을 때 import 문법으로 동작합니다. 공식 문서의 첫 예제는 const express = require('express') 형태이며 둘 다 됩니다. 상태 코드는 11주차 표에서 서버 쪽으로 자주 쓰는 것만 다시 모았습니다.

응답을 두 번 보냅니다

res.status(404).json(…) 뒤에 return이 없으면 아래 줄의 res.json(note)까지 실행됩니다. 실제 Express는 Cannot set headers after they are sent 오류를 냅니다. 또 하나, req.params.id는 문자열 '2'입니다. Number()로 바꾸지 않으면 '2' === 2가 거짓이라 늘 404가 납니다.

AI가 준 코드가 Express 4라면

AI의 학습 데이터에는 Express 4 코드가 많습니다. 현재 버전은 5.3.0이고 npm install express를 하면 5가 설치됩니다. 아래 줄이 보이면 고칩니다.

Express 4 문법과 Express 5의 차이 (공식 이전 안내 기준)
AI가 준 코드(4)Express 5에서는
res.send(404)res.sendStatus(404)
res.json(obj, 201)res.status(201).json(obj)
req.param('id')req.params.id (또는 req.body, req.query)
app.del(…)app.delete(…)
app.get('*', …)app.get('/*splat', …) — 와일드카드에 이름이 필요합니다
async 핸들러 끝에 .catch(next)필요 없습니다. 거부된 Promise는 오류 미들웨어로 자동 전달됩니다.
req.body가 항상 객체라고 가정express.json()이 없으면 undefined입니다. 미들웨어를 먼저 두세요.

입력은 믿지 않습니다: 검증과 오류 처리

3주차에 폼에 required를 붙였습니다. 그 검사는 브라우저에서만 일어납니다. 서버에는 폼을 거치지 않은 요청도 옵니다. 터미널에서 curl로 아무 본문이나 보낼 수 있고, 다른 사람이 만든 화면에서 보낼 수도 있습니다. 그래서 서버는 받은 값을 처음 보는 것처럼 다시 검사합니다.

const CATEGORIES = ['수업', '할 일', '아이디어'];

app.post('/api/notes', (req, res) => {
  const title = typeof req.body.title === 'string' ? req.body.title.trim() : '';
  if (!title || title.length > 100) {
    return res.status(400).json({ error: 'Bad Request', message: '제목은 1~100자여야 합니다' });
  }
  if (!CATEGORIES.includes(req.body.category)) {
    return res.status(400).json({ error: 'Bad Request', message: '분류가 올바르지 않습니다' });
  }
  const note = { id: Date.now(), title, category: req.body.category };
  notes.push(note);
  res.status(201).json(note);
});

검사 순서는 늘 같습니다. 타입 확인 → 빈 값·길이 → 허용 목록 → 저장. 오류 응답은 { error, message } 두 칸으로 통일하면 화면 쪽 코드가 data.message 하나만 보면 됩니다.

해 볼 것: 화면에서 제목을 비우고 추가를 눌러 보세요. 고치기 전에는 빈 메모가 목록에 들어가고, 고친 뒤에는 상태 줄에 400 · 제목은 1~100자여야 합니다가 보여야 합니다.

SQL을 쓴다면: 값은 문장에 이어 붙이지 않습니다

데이터베이스에 SQL로 묻기 시작하면 검증만으로는 부족합니다. 사용자가 보낸 값을 SQL 문장에 문자열로 이어 붙이면, 값 안에 든 따옴표와 명령이 문장의 일부가 됩니다. 이것이 SQL 인젝션입니다. 값은 ? 자리에 따로 넘깁니다(매개변수 바인딩). 라이브러리마다 메서드 이름은 다르지만 모양은 같습니다.

const id = req.params.id;
// id가 "1 OR 1=1" 이면 모든 행이 나옵니다
const row = db.query(`SELECT * FROM notes WHERE id = ${id}`);
const id = Number(req.params.id);
// 문장은 고정, 값은 따로 전달 (형태만 보여 주는 예)
const row = db.prepare('SELECT * FROM notes WHERE id = ?').get(id);

로그와 오류 응답의 형식을 하나로

내부 동작
Express는 핸들러가 next(err)를 부르거나, throw하거나, async 함수가 거부되면(5부터 자동) 인자가 네 개인 미들웨어로 건너뜁니다. 그 미들웨어는 등록 순서상 마지막이어야 합니다. 거기서 로그를 남기고(요청 메서드·경로·오류 메시지·시각), 클라이언트에는 정해진 모양 { error, message }만 돌려줍니다. 스택 트레이스는 로그에만 둡니다. 화면 코드는 상태 코드가 무엇이든 data.message 한 줄만 보여 주면 됩니다.
명세·문서
Express 5 이전 안내(거부된 Promise의 자동 전달) · MDN · HTTP 상태 코드
트레이드오프
메시지가 자세하면 개발할 때 편하지만, 그대로 내보내면 내부 구조(테이블 이름, 파일 경로)가 새어 나갑니다. 400대는 사용자가 고칠 수 있게 구체적으로, 500대는 "잠시 뒤 다시 시도" 수준으로 짧게 쓰고 자세한 것은 로그에 둡니다.
5분 실험
실습 2의 서버 탭에서 app.get('/api/notes', …) 핸들러 첫 줄에 throw new Error('디스크 읽기 실패');를 넣고 실행해 보세요. 연습용 서버는 오류 미들웨어를 흉내 내지 않고 자동으로 500과 { "error": "디스크 읽기 실패" }를 돌려줍니다. 네트워크 탭에서 500을 확인하고, 콘솔에서 로그 줄을 찾으세요. 실제 서버라면 이 메시지를 그대로 내보내도 되는지 판단하는 것이 여러분의 일입니다.

데이터는 어디에 남기나

위 예제의 notes 배열은 서버의 메모리에 있습니다. 서버를 끄면 사라집니다. 저장은 단계적으로 올립니다. 알파 버전은 메모리나 JSON 파일로 충분한 경우가 많습니다.

import { readFile, writeFile } from 'node:fs/promises';

const FILE = new URL('./notes.json', import.meta.url);

export async function loadNotes() {
  try { return JSON.parse(await readFile(FILE, 'utf8')); }
  catch { return []; }                     // 파일이 아직 없으면 빈 목록
}

export async function saveNotes(notes) {
  await writeFile(FILE, JSON.stringify(notes, null, 2));
}

SQLite로 올릴 때는 better-sqlite3 패키지나 Node.js에 내장되기 시작한 node:sqlite 모듈을 씁니다. 어느 쪽이든 위의 "자리와 값을 분리"하는 모양으로 묻습니다.

수업 직전 확인

node:sqlite는 수업 시점에 안정화 단계일 수 있습니다. 팀이 SQLite를 고르면 설치하기 전에 Node.js 공식 문서에서 현재 상태를 확인하고, 불확실하면 better-sqlite3를 씁니다. 무료 호스팅의 서버 파일은 재배포·재시작 때 초기화되는 경우가 많으므로 파일에 남긴 데이터는 백업이 필요합니다.

세션과 JWT: "누가 보냈나"를 서버가 기억하는 두 방식

내부 동작
세션은 서버가 로그인 상태를 저장소에 두고, 브라우저에는 그 열쇠(세션 id)만 쿠키로 줍니다. 요청마다 서버가 저장소를 조회합니다. JWT는 서버가 서명한 토큰(사용자 id·만료 시각 등)을 브라우저가 들고 다니고, 요청마다 Authorization: Bearer <토큰> 헤더로 보냅니다. 서버는 저장소 없이 서명만 검증합니다. 두 방식 모두 "검증 → 통과하면 다음 핸들러" 미들웨어 한 개로 구현됩니다.
명세·문서
RFC 7519 · JSON Web Token · MDN · HTTP 쿠키 · MDN · 401과 403
트레이드오프
세션은 서버에서 즉시 무효화할 수 있지만 저장소가 필요하고 서버가 여러 대면 공유해야 합니다. JWT는 서버가 상태를 안 가져 가볍지만, 만료 전에는 취소하기 어렵고 토큰이 새면 그 시간 동안 유효합니다. 학기 프로젝트에서 로그인이 필요하면 직접 구현하기보다 BaaS의 인증(선택 모듈 3)을 쓰는 편이 안전합니다.
5분 실험
아래 서버는 삭제 라우트 앞에 requireAuth 미들웨어를 두었지만 아직 아무것도 검사하지 않습니다. TODO를 채워 토큰이 없거나 틀리면 401을 돌려주세요. 실제 서버라면 VALID와 비교하는 자리에 서명 검증이나 세션 조회가 들어갑니다.

CORS, 환경 변수, 실행

화면은 GitHub Pages(https://팀.github.io)에, 서버는 다른 주소에 있습니다. 출처가 다르면 브라우저는 서버가 허용 헤더를 보내 줄 때만 응답을 JS에 넘깁니다. 이것이 CORS이고, 11주차에서 본 대로 브라우저가 지키는 규칙입니다. 서버가 헤더를 주지 않으면 콘솔에 Reason: CORS header 'Access-Control-Allow-Origin' missing이 뜨고, 코드는 오류가 났다는 것만 압니다.

import cors from 'cors';                 // npm install cors

// 개발 중에는 모두 허용, 배포 때는 우리 화면의 출처만
app.use(cors({ origin: process.env.ALLOWED_ORIGIN ?? '*' }));

const PORT = process.env.PORT ?? 3000;   // 호스팅 서비스가 PORT를 정해 줍니다
app.listen(PORT, () => console.log('listening on ' + PORT));

Content-Type: application/json인 POST는 "단순 요청"이 아니라서 브라우저가 먼저 OPTIONS 요청(프리플라이트)을 보냅니다. cors() 미들웨어가 그 응답까지 처리합니다. 네트워크 탭에 OPTIONS 줄이 보여도 놀라지 마세요.

비밀 키·허용 출처·포트처럼 환경마다 다른 값은 코드에 쓰지 않고 환경 변수로 둡니다. 로컬에서는 .env 파일, 배포 서비스에서는 대시보드의 환경 변수 칸입니다. .env는 .gitignore에 넣습니다. 한 번 커밋된 키는 지워도 이력에 남으므로 재발급합니다.

$ node --watch index.js
# 파일을 저장할 때마다 서버가 다시 시작됩니다. 끌 때는 Ctrl+C

Pages에서 localhost를 부릅니다

https://팀.github.io에 올린 화면에서 http://localhost:3000을 부르면 다른 사람의 컴퓨터에는 그 서버가 없습니다. 서버 주소는 배포 주소로 바꾸고, https로 맞춥니다. 개발·배포 주소를 한 곳에서 고르는 줄을 둡니다: const API = location.hostname === 'localhost' ? 'http://localhost:3000' : 'https://우리-서버-주소';

실습: 메모 분류 API를 끝까지

목록 · 분류별 보기 · 추가 · 삭제가 한 화면에서 돌아갑니다. 서버 탭에는 DELETE 라우트만 비어 있습니다. 네 번째 테스트를 통과시키세요. 그다음 네트워크 탭에서 지연을 3초로, 오프라인으로 바꿔 11주차의 세 가지 상태가 화면에 나오는지 확인합니다.

해 볼 것 세 가지입니다. ① 네트워크 탭에서 POST 줄을 골라 보낸 본문과 받은 201을 읽습니다. ② 지연을 3초로 바꾸고 추가를 눌러 '불러오는 중…'이 보이는지 확인합니다. ③ 오프라인으로 바꾸고 전체 보기를 눌러 '불러오지 못했습니다'가 나오는지 확인합니다. 세 상태가 모두 보이면 서버 쪽은 끝입니다.

헬스 체크: 서버가 살아 있는지 묻는 가장 작은 라우트

내부 동작

MDN · HTTP 상태 코드(200과 503의 뜻) · Express 5 API(res.json)
트레이드오프
헬스 체크가 DB까지 확인하면 더 정확하지만 느려지고, DB가 잠시 느릴 때 서버 전체가 "죽었다"고 판정될 수 있습니다. 보통은 가볍게(프로세스가 응답하는가) 두고, DB 상태는 별도 항목으로 돌려줍니다.
5분 실험

무료로 시작할 수 있지만 유료 전환은 서비스마다 월 몇 달러에서 수십 달러까지 다릅니다(Supabase Pro는 월 25달러부터). 학기 프로젝트는 무료 한도 안에서 설계합니다. 유료 여부가 평가에 영향을 주지 않습니다.

요청 제한(rate limit): 10초에 다섯 번까지

내부 동작
클라이언트를 구분하는 열쇠(IP 주소, 토큰, 사용자 id)마다 최근 요청 시각을 기억하고, 정해진 창(window) 안의 개수가 한도를 넘으면 429 Too Many Requests와 Retry-After 헤더(몇 초 뒤에 다시)를 돌려줍니다. 라우트 앞의 미들웨어 하나로 구현하며, 서버가 여러 대면 기억을 공유 저장소(Redis 등)에 둡니다.
명세·문서
MDN · HTTP 상태 코드(429) · Express 5 API(app.use, res.set)
트레이드오프
너무 엄격하면 정상 사용자를 막습니다. 특히 같은 교실 Wi-Fi에서는 수강생 전체가 같은 IP로 보일 수 있습니다. 시연 날에는 한도를 넉넉히 두거나 열쇠를 토큰·사용자 단위로 바꿉니다. 느슨하면 방어가 안 됩니다. 한도는 로그를 보며 조정합니다.
