테스트: 체크리스트 한 줄을 자동으로 확인하기

10주차에 만든 tests/checklist.md는 사람이 매번 눈으로 확인하는 목록입니다. 이 모듈에서는 그중 한 줄을 코드로 옮겨, 바꿀 때마다 1분 안에 "아직 맞다"를 확인하는 방법을 익힙니다. 실습은 모두 브라우저 안의 연습용 러너에서 돌아갑니다. 마지막에는 우리 팀에 어떤 테스트가 얼마나 필요한지 결정표로 답합니다.

  • 예상 시간 읽기 20~30분 · 실습 30분
  • 먼저 볼 것 10주차 저장소·기본 하네스(tests/checklist.md), 12주차 AI 코드 검토와 테스트 입문 (교안 지도에서 엽니다)
  • 기본 도구 ChatGPT Edu(기본) · 에이전트(Codex 또는 Claude Code)
  • AI 등급 AI ALLOWED

이 모듈이 맞는 프로젝트

잘 맞는 경우
  • 계산하거나 분류하는 규칙이 있습니다. 예: 메모를 제목으로 분류한다, 점수를 더한다, 마감이 지났는지 판단한다.
  • 여러 사람이 같은 파일을 고칩니다. 팀원 1이 고친 뒤 팀원 2의 기능이 깨졌는지 PR마다 확인하고 싶습니다.
  • AI가 코드를 많이 씁니다. 사람이 매번 다 읽기 어려우니 1차 검사를 코드에 맡기고 싶습니다.
  • 13주차 알파 테스트 뒤에 고칠 것이 많습니다. 고치면서 다른 곳이 깨지지 않게 지키고 싶습니다.
과한 경우
  • 화면이 한두 개이고 규칙이 거의 없습니다. tests/checklist.md를 손으로 확인하는 편이 빠릅니다.
  • 베타 시연까지 일주일이 남았고 아직 알파가 안 돕니다. 지금은 테스트보다 사용 장면 하나를 끝까지 지나가는 일이 먼저입니다.
  • E2E 테스트를 열 개 넘게 쓰려 합니다. 알파 단계에서는 단위 테스트 한두 개와 E2E 하나면 충분합니다.
먼저 할 것
팀 저장소에 tests/checklist.md가 있고, 그 안에 "이러면 맞다"가 한 줄 이상 적혀 있어야 합니다. 터미널에서 node -v가 22.12 이상이면 준비는 끝입니다(수업 권장 24 LTS). 12주차 교안의 테스트 입문을 먼저 읽으면 이 모듈이 쉬워집니다.

진행 상황을 표시하며 따라가세요. 표시는 이 브라우저에만 저장됩니다.

테스트가 보장하는 것

테스트는 "이러면 맞다"를 코드로 적어 둔 것입니다. 사람이 확인하던 한 줄을 컴퓨터가 대신 확인합니다.

10주차의 tests/checklist.md에는 이런 줄이 있습니다. "제목에 '시험'이 들어간 메모는 '수업'으로 분류된다." 지금은 팀원이 화면에서 메모를 하나 써 보고 눈으로 확인합니다. 코드를 바꿀 때마다 같은 일을 반복합니다. 이 한 줄을 함수 호출 한 번과 expect 한 줄로 옮기면, 바꾼 뒤 명령 하나로 1분 안에 "아직 맞다"를 알 수 있습니다.

보장하는 것
적어 둔 경우가 지금도 같은 결과를 냅니다(회귀 방지). 바꾼 뒤 바로 확인할 수 있습니다. AI가 만든 변경을 사람보다 먼저 검사합니다.
보장하지 않는 것
적지 않은 경우. 테스트 자체가 틀린 경우(아래 실습 4). 사용자가 화면을 이해하는지 — 이것은 13주차 알파 테스트의 몫입니다.

"테스트를 다 통과했으니 맞다"

통과하는 테스트와 맞는 테스트는 다릅니다. 테스트는 적어 둔 경우만 봅니다. 적어 둔 기대값이 틀렸거나 구현을 그대로 베꼈다면, 버그가 있어도 초록불이 켜집니다. 실습 4에서 직접 확인합니다.

핵심 개념 다섯 가지

단위 테스트의 모양, 가짜로 바꾸기, 브라우저 E2E, 접근성 자동 검사, 불안정 테스트. 다섯 개념을 최소 예제로 읽습니다.

1. 단위 테스트의 모양: 준비 → 실행 → 확인

단위 테스트는 함수 하나를 부르고 결과를 확인합니다. 세 부분으로 읽습니다. 준비(입력을 만든다) → 실행(함수를 부른다) → 확인(expect로 기대값과 비교한다). Vitest의 공식 최소 예제입니다.

export function sum(a, b) {
  return a + b
}
import { expect, test } from 'vitest'
import { sum } from './sum.js'

test('adds 1 + 2 to equal 3', () => {
  expect(sum(1, 2)).toBe(3)
})

파일 이름에 .test. 또는 .spec.이 있어야 Vitest가 찾습니다. 한 번만 돌리려면 npx vitest run, 바꿀 때마다 자동으로 다시 돌리려면 npm run test(감시 모드)입니다. Vitest 5는 Node 22.12 이상이 필요합니다. 테스트 이름은 "이러면 맞다"를 한국어 문장으로 씁니다. 실패했을 때 무엇이 틀렸는지 이름만 보고 알 수 있어야 합니다.

2. 테스트 더블: fetch를 가짜로

화면 코드는 fetch로 서버를 부릅니다. 테스트할 때마다 진짜 서버를 켤 수는 없습니다. 그래서 테스트 더블을 세웁니다. Vitest에서는 vi.fn()으로 가짜 함수를 만들고 vi.stubGlobal()로 전역 fetch를 바꿔치기합니다. 실습 2에서는 같은 생각을 연습용 러너 안에서 해 봅니다.

import { expect, test, vi } from 'vitest'
import { loadNotes } from './notes.js'

test('서버가 준 메모 2개를 돌려준다', async () => {
  // 준비: fetch를 "항상 메모 2개를 주는 가짜"로 바꿉니다
  vi.stubGlobal('fetch', vi.fn(async () =>
    new Response(JSON.stringify([{ title: '시험 준비' }, { title: '팀 회의 메모' }]))
  ))
  // 실행
  const notes = await loadNotes('/api/notes')
  // 확인
  expect(notes).toHaveLength(2)
  expect(fetch).toHaveBeenCalledWith('/api/notes')
})

가짜는 두 종류를 구별해 둡니다. 함수 단위의 가짜(위 코드)는 빠르고 어떤 값이든 흉내 낼 수 있습니다. 네트워크 단위의 가짜(연습용 서버, 실제 프로젝트에서는 선택 모듈 2의 Express 서버를 테스트 전용 데이터로 띄우는 것)는 더 느리지만 요청과 응답의 모양까지 확인합니다.

3. 브라우저 E2E: Playwright와 getByRole

E2E는 진짜 브라우저를 열고 사용자처럼 누릅니다. Playwright 공식 예제를 우리 메모 앱에 맞춰 읽습니다. 요소를 찾을 때 CSS 선택자 대신 getByRole을 씁니다. 역할(button, heading, link)과 이름(사용자가 읽는 글자)으로 찾기 때문에, 접근성이 좋은 화면일수록 테스트도 쉽게 써집니다.

import { test, expect } from '@playwright/test';

test('메모를 추가하면 목록에 한 줄이 늘어난다', async ({ page }) => {
  await page.goto('/');                       // baseURL: http://localhost:5173

  await page.getByRole('textbox', { name: '제목' }).fill('시험 준비');
  await page.getByRole('button', { name: '추가' }).click();

  await expect(page.getByRole('listitem').filter({ hasText: '시험 준비' })).toBeVisible();
});

page.goto('/')가 되려면 playwright.config의 baseURL을 http://localhost:5173(Vite 개발 서버)로 두고, 테스트 전에 npm run dev가 떠 있어야 합니다. getByRole('textbox', { name: '제목' })이 되려면 입력창에 <label>이 연결되어 있어야 합니다. 3주차의 폼 규칙이 여기서 다시 쓰입니다.

4. 접근성 자동 검사: axe

axe-core는 페이지를 읽고 접근성 규칙 위반(라벨 없는 입력, 대비 부족, alt 없는 이미지 등)을 목록으로 돌려줍니다. Playwright와 함께 쓰면 E2E 테스트 한 개에 한 줄만 더하면 됩니다.

const { AxeBuilder } = require('@axe-core/playwright');

test('첫 화면에 접근성 위반이 없다', async ({ page }) => {
  await page.goto('/');
  const results = await new AxeBuilder({ page }).analyze();
  expect(results.violations).toEqual([]);
});

가장 쉬운 길은 브라우저 확장 프로그램 axe DevTools입니다. 설치 없이 결과만 보고 싶다면 Chrome DevTools의 Lighthouse 패널에서 Accessibility 항목을 봅니다. 자동 검사는 기계가 판단할 수 있는 규칙만 봅니다. 키보드로 끝까지 한 번 가 보는 일은 여전히 사람이 합니다.

5. 불안정 테스트의 원인 세 가지

불안정 테스트는 신뢰를 잃게 합니다. 한 번 "그냥 다시 돌리면 돼"가 되면 아무도 빨간불을 보지 않습니다. 원인은 거의 셋 중 하나입니다.

불안정 테스트의 원인과 처방
원인증상처방
타이머wait(50)처럼 고정 시간을 기다립니다. 느린 컴퓨터나 CI에서 실패합니다.시간이 아니라 조건을 기다립니다. until(() => 목록이 2개), Playwright의 expect(...).toBeVisible()(자동 재시도).
네트워크진짜 서버·외부 API를 부릅니다. 서버가 느리거나 데이터가 바뀌면 실패합니다.가짜(더블)로 바꿉니다. E2E는 테스트 전용 데이터로 띄운 서버를 씁니다.
순서앞 테스트가 남긴 데이터(전역 변수, 저장소)에 뒤 테스트가 기댑니다. 혼자 돌리면 통과, 같이 돌리면 실패.테스트마다 준비를 새로 하고, 끝나면 되돌립니다(실습 2의 finally).

테스트 데이터 빌더: 기본값은 한 곳에

내부 동작
테스트마다 { id, title, category, done, due }를 전부 적으면, 메모에 필드 하나가 늘 때 테스트 스무 개를 고쳐야 합니다. 빌더는 "보통의 메모"를 돌려주는 함수 하나(makeNote(overrides))에 기본값을 모아 두고, 테스트는 그 테스트에서 중요한 필드만 덮어씁니다. 구현은 객체 펼치기({ ...defaults, ...overrides }) 한 줄입니다. 5주차 참고 파트의 '값을 꺼내고 배열·객체를 펼치기'가 여기서 쓰입니다.
명세·문서
Vitest Guide(테스트 파일 구조) · MDN · Promise(비동기 테스트가 기다리는 것)
트레이드오프
빌더가 똑똑해질수록(무작위 값, 연쇄 호출) 테스트를 읽을 때 "이 값이 어디서 왔지?"가 늘어납니다. 기본값은 고정된 평범한 값으로 두고, 테스트가 기대는 값은 그 테스트 안에서 눈에 보이게 덮어씁니다.
5분 실험
아래 빌더에는 기본 마감일이 없어서 첫 테스트가 실패합니다. 테스트 탭의 TODO를 채워 기본값 한 줄을 넣고, 세 테스트가 모두 통과하는지 보세요. 그다음 isOverdue에 "마감 당일은 지나지 않은 것"이라는 규칙을 테스트로 먼저 적고 구현을 바꿔 보세요.

실습: 체크리스트 한 줄을 테스트로

연습용 러너는 Vitest와 같은 test·expect를 씁니다. 네 실습 모두 처음에는 테스트 하나가 실패합니다. 어느 탭을 고쳐야 하는지가 실습마다 다릅니다.

체크리스트 줄이 테스트 이름이 됩니다
tests/checklist.md의 한 줄테스트 이름층

서버가 오류를 내면 화면에 상태 코드가 보인다서버가 500으로 답하면 상태 코드를 알려 준다통합 (실습 2)

실습 1 · 분류 함수에 단위 테스트

JS 탭의 categorize는 '회의' 규칙이 빠져 있습니다. 테스트 탭을 먼저 읽고, 어떤 문장이 실패하는지 본 뒤 JS 탭의 TODO를 채우세요. 테스트는 고치지 않습니다.

실습 2 · fetch를 가짜로 바꾸고 오류 응답 확인하기

테스트 탭에 더블이 두 종류 있습니다. 첫 테스트는 window.fetch 자체를 가짜 함수로 바꿉니다(Vitest의 vi.stubGlobal과 같은 생각). 둘째 테스트는 연습용 서버의 /api/broken이 500을 돌려줍니다. JS 탭의 loadNotes는 아직 res.ok를 보지 않아서 둘째 테스트가 실패합니다. TODO를 채우세요.

고친 뒤 네트워크 탭을 보세요. 첫 테스트는 요청이 기록되지 않습니다. 가짜 함수가 서버에 가기 전에 답했기 때문입니다. 둘째 테스트는 500 한 줄이 남습니다.

실습 3 · 불안정 테스트 고치기

이번에는 JS가 아니라 테스트 탭이 틀렸습니다. 첫 테스트는 50ms만 기다리고 목록을 셉니다. 네트워크 탭에서 지연을 0으로 바꾸면 통과하고, 300ms로 두면 실패합니다. 코드는 그대로인데 결과가 달라지는 것, 이것이 불안정 테스트입니다. 고정 시간 대신 조건을 기다리도록 바꾸세요.

실습 4 · 구현을 베낀 테스트 찾기

AI에게 "이 함수의 테스트를 써 줘"라고 하면, 기대값을 손으로 적는 대신 구현과 같은 식으로 계산하는 테스트가 자주 나옵니다. 그런 테스트는 버그가 있어도 통과합니다. 아래 JS의 countByCategory에는 버그가 하나 있습니다. 테스트 A는 통과하고 B는 실패합니다. 순서대로 해 보세요.

  1. 실행해서 A는 초록, B는 빨강인 것을 봅니다. B의 메시지에서 실제 결과를 읽습니다.
  2. JS 탭의 버그를 고칩니다. 힌트: 빈 문자열 ''은 ??를 그냥 지나갑니다(5주차 참고 파트 '중간 객체가 없을 때의 속성 접근').
  3. 다시 실행합니다. 이제 B는 통과하고 A가 실패합니다. 구현을 베낀 테스트는 버그를 지키는 테스트였습니다. A의 기대값을 구체적인 값으로 다시 쓰세요.

스냅샷 테스트의 함정

내부 동작
스냅샷 테스트는 결과(HTML 문자열, 큰 객체)를 통째로 파일에 저장해 두고, 다음 실행에서 바이트 단위로 같은지 비교합니다. 쓰기는 쉽습니다. 기대값을 적지 않아도 되니까요. 그런데 바로 그 이유로 "무엇이 맞는지"를 아무도 적지 않은 테스트가 됩니다. 클래스 하나, 공백 하나가 바뀌어도 빨간불이 켜지고, 사람은 읽지 않고 스냅샷을 갱신합니다. 그 순간 버그도 함께 저장됩니다.
명세·문서
Vitest Guide(Snapshot 항목) · Playwright · Writing tests(행동 기준 assertion)
트레이드오프
스냅샷은 "바뀌었다"는 사실을 빨리 알려 줍니다. 디자인 시스템의 마크업처럼 바뀌면 안 되는 출력에는 맞습니다. 사용자가 보는 행동(글자가 보인다, 버튼이 늘어난다)을 확인하고 싶다면 그 행동을 적은 테스트가 낫습니다. 둘을 섞을 때는 스냅샷이 실패하면 반드시 diff를 읽는다는 규칙을 하네스에 적습니다.
5분 실험
아래 테스트 A는 어제 저장한 HTML 문자열과 비교합니다. 오늘 디자인 담당 팀원이 <li>에 클래스를 하나 붙였고, 화면은 멀쩡한데 A가 실패합니다. A를 "제목과 분류가 보인다"처럼 행동을 적는 테스트로 바꾸거나, 스냅샷을 갱신하기 전에 무엇이 바뀌었는지 읽어 보세요.

커버리지는 정확성이 아닙니다

내부 동작
커버리지 도구는 테스트가 도는 동안 어떤 줄(또는 분기)이 한 번이라도 실행되었는지 셉니다. "실행되었다"와 "맞는지 확인했다"는 다릅니다. 실습 4의 테스트 A만 남기면 countByCategory의 모든 줄이 실행되어 커버리지는 100%지만, 빈 분류 버그는 그대로입니다. 커버리지가 낮은 곳은 "아직 안 본 곳"을 알려 주는 지도로만 씁니다.
명세·문서
Vitest Guide(Coverage 항목)
트레이드오프
숫자 목표(예: 80%)를 두면 숫자를 채우는 테스트가 늘어납니다. 그 테스트는 대개 기대값이 없거나 구현을 베낀 것입니다. 팀 규칙은 숫자 대신 "★ 장면의 순수 함수에는 테스트가 있다"처럼 장소로 정합니다.
5분 실험
실습 4에서 테스트 B를 지우고 실행해 보세요. 모든 테스트가 통과하고 함수의 모든 줄이 실행됩니다. 그래도 '' 분류는 '기타'로 세지 않습니다. B를 되살리고, 기대값이 구체적인 값인 테스트만이 버그를 잡는다는 것을 확인하세요.

확인 문제

Q1테스트 피라미드에서 가장 많이 두는 층은?

  • 맞습니다. 작고 빠르고 깨지는 이유가 분명해서 많이 둘 수 있습니다.

  • E2E는 사용자에 가깝지만 느리고 타이머·네트워크·순서에 흔들립니다. ★ 장면 하나에만 둡니다.

  • 수동 체크리스트는 피라미드의 층이 아니라, 아직 코드로 옮기지 않은 "이러면 맞다"의 목록입니다.

Q2Vitest 테스트를 감시 모드 없이 한 번만 돌리는 명령을 쓰세요.

npx vitest run입니다. npm run test는 "test": "vitest"일 때 감시 모드로 들어갑니다. 에이전트나 CI에서는 한 번만 도는 명령을 씁니다.

Q3불안정 테스트의 흔한 원인을 모두 고르세요.

  • 맞습니다. 느린 컴퓨터나 CI에서 시간이 모자랍니다. 조건을 기다리도록 바꿉니다.

  • 맞습니다. 서버 상태와 데이터가 바뀌면 결과도 바뀝니다. 더블로 바꿉니다.

  • 맞습니다. 혼자 돌리면 통과하고 같이 돌리면 실패합니다. 테스트마다 준비하고 되돌립니다.

  • 이름의 언어는 결과와 무관합니다. 오히려 실패했을 때 읽기 쉬운 한국어 문장을 권합니다.

Q4Playwright에서 '추가' 버튼을 찾는 방법으로 가장 권장되는 것은?

  • 클래스 이름은 디자인이 바뀌면 함께 바뀝니다. 사용자가 보는 것과도 무관합니다.

  • 맞습니다. 역할과 이름으로 찾으면 사용자가 보는 방식과 같고, 접근성이 좋은 화면일수록 잘 찾힙니다.

  • 구조에 기대는 선택자는 요소 하나만 끼어들어도 깨집니다.

Q5다음 중 '구현을 베낀 테스트'는?

  • 기대값 3을 사람이 적었습니다. 좋은 테스트입니다.

  • 항상 참인 테스트입니다. 베낀 것은 아니지만 아무것도 확인하지 않습니다. 이것도 함정입니다.

  • 맞습니다. 기대값을 구현과 같은 방법으로 계산합니다. 구현에 버그가 있으면 기대값도 같이 틀려서 통과합니다.

실제 프로젝트에 붙이는 순서

단위 테스트 한 개부터 시작합니다. 10분이면 됩니다. Playwright·axe·CI는 알파가 돈 뒤에 하나씩 더합니다.

  1. 버전 확인node -v가 22.12 이상이어야 합니다(수업 권장 24 LTS). 낮으면 nodejs.org에서 24를 설치합니다.
  2. Vitest 설치와 첫 테스트순수 함수 하나를 src/로 꺼내 export하고, 옆에 .test.js를 만듭니다.
  3. 하네스에 적기AGENTS.md(또는 CLAUDE.md)에 테스트 명령과 "바꾼 뒤 실행하고 결과를 보여 줄 것"을 적습니다.
  4. Playwright + axe (선택)★ 사용 장면 하나에 E2E 1개, 첫 화면에 axe 검사 1개.
  5. CI (선택)GitHub Actions가 PR마다 npx vitest run을 돌리게 합니다.

2단계 · 하네스에 적기

## 테스트
- 단위 테스트: `npx vitest run` (한 번만 실행). 감시 모드 `npm run test`는 사람만 씁니다.
- JavaScript 파일을 바꾼 뒤에는 반드시 `npx vitest run`을 실행하고 출력을 보여 줄 것.
- 테스트의 기대값은 계산식이 아니라 구체적인 값으로 쓸 것.
- 실패한 테스트를 지우거나 스냅샷을 갱신하지 말고, 먼저 무엇이 바뀌었는지 보고할 것.

Codex는 작업 전에 AGENTS.md를 읽고, Claude Code는 CLAUDE.md를 읽되 AGENTS.md도 읽을 수 있습니다. 10주차에 정한 대로 AGENTS.md 하나에 적고 CLAUDE.md에서 가져오면 두 도구가 같은 규칙을 봅니다. Claude Code가 npm test를 돌리려 할 때 권한 프롬프트가 뜨면, "Yes, and don't ask again for: npm test *"처럼 테스트 명령만 허용해 두면 됩니다.

3단계 · Playwright와 axe (선택)

$ npm init playwright@latest
$ npm install @axe-core/playwright
$ npx playwright test
$ npx playwright show-report
$ npx playwright test --ui

npm init playwright@latest는 TypeScript/JavaScript, 테스트 폴더 이름, GitHub Actions 워크플로를 추가할지, 브라우저를 설치할지를 묻고 playwright.config와 tests/example.spec을 만듭니다. 설정에서 baseURL을 http://localhost:5173으로 두고, 테스트에서는 page.goto('/')로 엽니다. 02의 3·4번 코드를 tests/e2e/에 옮기면 됩니다.

4단계 · CI (선택)

CI는 "PR을 올릴 때마다 남의 컴퓨터에서 테스트를 돌려 주는 것"입니다. 6주차의 GitHub Pages 배포가 Actions로 되어 있다면 같은 폴더에 파일 하나를 더합니다.

name: Tests

on:
  push:
    branches: ["main"]
  pull_request:

jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - run: npm ci
      - run: npx vitest run

수업 직전 확인

위 워크플로의 액션 버전 표기(actions/setup-node@v4)와 npm init playwright@latest가 만들어 주는 워크플로 파일의 현재 내용은 수업 직전에 GitHub·Playwright 공식 문서에서 확인합니다. 액션 버전이 달라도 단계의 순서(받기 → Node 준비 → 설치 → 테스트)는 같습니다.

PR 화면에서 초록 체크가 보이면 병합하고, 빨간 X면 로그를 열어 어느 테스트가 왜 실패했는지 PR 본문에 한 줄 적습니다. 이 줄이 12주차 교차 검토의 '동작' 묶음 증거가 됩니다.

AI에게 맡길 일 · 직접 판단할 일

이 모듈의 AI 단계는 Test와 Inspect입니다. 테스트의 초안은 AI가 빨리 씁니다. 무엇이 맞는지(기대값)와 무엇을 테스트할지(장소)는 여러분이 정합니다. "AI가 다 해 줘도 되나요?"의 답은 늘 같습니다. 설명·검증·판단을 할 수 있으면 됩니다.

에이전트의 리뷰 명령(Claude Code /review, Codex /review)에 "이 테스트가 구현을 베끼고 있는지, 기대값이 구체적인지 봐 줘"라고 덧붙이면 실습 4의 A 같은 테스트를 찾아 줍니다. 다만 리뷰가 통과시켰다고 맞는 것은 아닙니다. 12주차의 "통과하는 리뷰 ≠ 맞는 리뷰"가 테스트에도 그대로 적용됩니다.
