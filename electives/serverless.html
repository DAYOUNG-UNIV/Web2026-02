서버리스와 BaaS

GitHub Pages는 파일만 돌려줍니다. "여러 사람이 같이 쓰는 데이터"와 "숨겨야 하는 키"가 생기는 순간, 요청마다 코드를 실행해 줄 곳이 필요합니다. 서버 한 대를 직접 돌보지 않고 그 일을 맡기는 두 가지 길을 봅니다.

  • 예상 시간 읽기 20~30분 + 실습 30분
  • 먼저 볼 것 11주차 fetch·JSON·세 가지 상태, 10주차 터미널·npm (교안 지도)
  • AI 등급 AI ALLOWED

이 모듈이 맞는 프로젝트

잘 맞는 경우
  • 사용자 여러 명이 같은 데이터를 보고 고쳐야 합니다. 예: 내 메모 분류 결과를 친구가 나눈 결과와 나란히 놓아 보기.
  • 외부 API를 부르는데 키를 브라우저에 둘 수 없습니다. (생성형 AI API, 지도·날씨 API)
  • 로그인이나 "내 것만 보기"가 팀 시트 ⑧의 ★ 단계에 들어 있습니다.
  • 서버 한 대를 학기 내내 켜 두고 돌볼 사람이 팀에 없습니다.
과한 경우
  • 데이터가 내 브라우저 안에만 있어도 되는 프로젝트. 11주차의 localStorage로 충분합니다.
  • 알파 버전에서 "여럿이 같이"가 가짜로 둘 것에 들어 있습니다. 알파는 가짜 데이터로 먼저 끝내고, 이 모듈은 알파 테스트 뒤에 붙여도 늦지 않습니다.
  • 팀원 모두가 터미널과 npm을 아직 한 번도 써 보지 않았습니다. 10주차 실습을 먼저 합니다.
먼저 할 것
팀 시트 ⑦의 데이터 표(받는 것·남기는 것·가져오는 것)와 ⑧ 알파 범위를 옆에 펼쳐 둡니다. "남기는 것" 칸에 적힌 데이터가 이 모듈의 대상입니다. 비어 있다면 이 모듈은 아직 필요 없습니다.

진행 상황을 표시하며 따라가세요. 표시는 이 브라우저에만 저장됩니다.

정적인가, 동적인가: 기준은 한 줄입니다

7주차 특강에서 나온 기준을 그대로 씁니다. 서버가 요청마다 코드를 실행하는가.

GitHub Pages는 요청이 오면 저장된 파일을 그대로 돌려줍니다. 코드를 실행하지 않습니다. 그래서 누가 와도 같은 HTML을 받고, 누가 보내도 저장되지 않습니다. 11주차까지 만든 메모 앱이 "내 브라우저에서만" 동작했던 이유가 이것입니다. 데이터는 localStorage, 즉 내 브라우저 안에 있었습니다.

이제 팀 프로젝트의 사용 장면을 한 줄씩 보고, 어느 줄에서 "요청마다 코드 실행"이 필요한지 표시합니다.

서버 한 대
Node.js + Express를 직접 켜 둡니다. 모든 것을 할 수 있지만, 켜 두고 돌보는 일도 우리 몫입니다. 백엔드 모듈에서 다룹니다.
서버리스 함수
"요청 하나를 받아 응답 하나를 돌려주는 함수"만 올립니다. 켜고 끄는 일은 플랫폼이 합니다. 키를 숨기는 프록시, 작은 API에 맞습니다.
BaaS
Backend as a Service. 데이터베이스·인증·파일 저장을 콘솔에서 만들고, 브라우저에서 바로 부릅니다. "여러 사람이 같이 쓰는 데이터"를 가장 빨리 얻는 길입니다.

"GitHub Pages에 올렸는데 저장이 안 돼요"

Pages는 POST를 받을 코드가 없습니다. 콘솔에 405나 404가 보이고, 새로고침하면 데이터가 사라집니다. 저장이 필요한 줄은 이 모듈의 함수나 BaaS로 보냅니다. 화면(HTML·CSS·JS)은 그대로 Pages에 둬도 됩니다.

함수 하나가 서버를 대신합니다

서버리스 함수의 모양은 플랫폼이 달라도 같습니다. 요청(Request)을 받아 응답(Response)을 돌려줍니다.

세 플랫폼의 공식 "첫 함수"를 나란히 봅니다. 파일 위치와 명령만 다르고, 함수 본문은 거의 같습니다. 고른 탭은 다음에 이 페이지를 열 때도 기억됩니다.

$ npm create cloudflare@latest -- my-first-worker
$ npx wrangler dev      # 로컬에서 실행
$ npx wrangler deploy   # *.workers.dev 주소로 배포
export default {
  async fetch(request, env, ctx) {
    return new Response("Hello World!");
  },
};

키 같은 비밀 값은 env로 들어옵니다. 저장소가 아니라 wrangler secret put으로 넣습니다.

export default {
  async fetch(request) {
    const response = await fetch('https://api.vercel.app/products');
    const products = await response.json();
    return Response.json(products);
  },
};

메모 API를 함수 모양으로 쓰면

11주차 메모 앱이 부르던 /api/memos를 Workers 모양으로 적어 봅니다. 경로와 메서드를 보고, 검사하고, 응답합니다. 이 세 단계는 어느 플랫폼이든 같습니다.

export default {
  async fetch(request, env) {
    const url = new URL(request.url);

    if (request.method === 'GET' && url.pathname === '/api/memos') {
      const memos = await readMemos(env);          // 데이터는 함수 밖(DB)에서 읽는다
      return Response.json(memos);
    }

    if (request.method === 'POST' && url.pathname === '/api/memos') {
      const body = await request.json();
      if (!body.text || !body.text.trim()) {
        return Response.json({ error: '본문이 비어 있습니다' }, { status: 400 });
      }
      const memo = await saveMemo(env, { text: body.text.trim(), tag: body.tag });
      return Response.json(memo, { status: 201 });
    }

    return new Response('Not Found', { status: 404 });
  },
};

한 가지가 눈에 띄어야 합니다. 메모를 함수 안의 배열에 넣지 않고 readMemos·saveMemo로 밖에 둡니다. 함수는 요청이 없으면 꺼지고, 다음 요청은 다른 복사본이 받을 수 있습니다. 함수 안의 변수는 "다음 요청까지 남아 있다"고 믿을 수 없습니다. 그래서 함수는 BaaS나 데이터베이스와 짝을 이룹니다.

"함수 안의 배열에 push 했는데 가끔 사라져요"

로컬(wrangler dev)에서는 되는 것처럼 보입니다. 배포하면 요청마다 다른 복사본이 받을 수 있어 목록이 비었다 찼다 합니다. 저장은 데이터베이스(03의 BaaS)에 합니다.

콜드 스타트: 첫 요청이 느린 이유

내부 동작
함수는 요청이 없으면 실행 환경째로 내려갑니다. 한참 만에 첫 요청이 오면 플랫폼이 실행 환경을 새로 띄우고 코드를 읽어 들인 뒤에야 핸들러가 돕니다. 그 준비 시간이 콜드 스타트입니다. 바로 이어진 두 번째 요청은 준비된 복사본이 받아 빠릅니다. 준비 시간은 플랫폼과 코드 크기(불러오는 라이브러리 양)에 따라 다릅니다.
명세·문서
Cloudflare Workers · Get started · Vercel Functions · Quickstart
트레이드오프
항상 켜진 서버는 첫 요청도 빠르지만 쉬는 시간에도 비용이 듭니다. 함수는 쉬는 동안 0원이지만 첫 요청이 느립니다. 시연처럼 "첫인상"이 중요한 자리에서는 시작 전에 한 번 불러 깨워 둡니다.
5분 실험
실습 1의 네트워크 탭에서 지연을 3초로 바꾸고 실행합니다. JS 탭 load() 앞뒤에 const t = performance.now()와 console.log(Math.round(performance.now() - t), 'ms')를 넣어 첫 요청 시간을 찍어 보세요. 그다음 지연을 0으로 되돌려 "깨어 있는 함수"와 비교합니다. 연습 서버는 매번 같은 지연을 주지만, 실제 플랫폼은 첫 요청만 느립니다.

엣지: 사용자 가까이에서 실행하기

내부 동작
Cloudflare Workers처럼 전 세계 여러 지역의 서버에 같은 함수를 복사해 두고, 요청을 보낸 사용자와 가까운 곳에서 실행하는 방식을 엣지(edge)라고 부릅니다. 요청이 바다를 건너지 않으니 왕복 시간이 줄어듭니다. 함수는 요청 헤더(언어, 지역, 기기)를 보고 응답을 바꾸는 일에 자주 쓰입니다.
명세·문서
Cloudflare Workers · Get started · MDN · CORS (다른 출처의 함수를 부를 때 필요한 헤더)
트레이드오프
함수는 가까워졌지만 데이터베이스는 보통 한 지역에 있습니다. 함수에서 DB까지의 왕복은 그대로라서, DB를 여러 번 부르는 함수는 엣지의 이점을 잃습니다. 또 엣지 실행 환경은 Node.js 전부가 아니라 Web 표준 API 위주라, 어떤 npm 패키지는 돌지 않습니다.
5분 실험
실습 1의 서버 탭에 app.get('/api/hello', (req, res) => res.send(req.get('x-user-lang') === 'ko' ? '안녕하세요' : 'Hello'))를 더합니다. JS 탭에서 fetch('/api/hello', { headers: { 'x-user-lang': 'ko' } })로 불러 응답을 콘솔에 찍어 보세요. 헤더 하나로 응답이 갈리는 것이 엣지 함수의 흔한 용도입니다.

함수 타임아웃: 오래 걸리는 일은 함수에 맞지 않습니다

내부 동작
플랫폼은 함수 한 번의 실행 시간이나 CPU 시간에 한도를 둡니다. 예를 들어 Workers Free 플랜은 요청당 CPU 시간 10 ms입니다(무엇이 CPU 시간에 포함되는지는 공식 Limits 문서가 기준입니다). 한도를 넘으면 플랫폼이 실행을 끊고 오류 응답을 돌려줍니다. 브라우저 쪽에서는 응답이 늦거나 5xx로 보입니다.
명세·문서
Cloudflare Workers · Get started(한도는 같은 문서 묶음의 Limits 항목) · MDN · AbortController
트레이드오프
영상 변환, 큰 파일 처리, 몇 분짜리 크롤링은 함수에 맞지 않습니다. 작업을 큐에 넣고 따로 처리하거나 서버 한 대(백엔드 모듈)를 씁니다. 대신 함수는 "1초 안에 끝나는 작은 일"을 아주 많이, 싸게 처리합니다.
5분 실험
실습 1의 서버 탭에 응답을 하지 않는 경로 app.get('/api/slow', (req, res) => { /* 아무것도 안 함 */ })를 더하고 JS 탭에서 불러 보세요. 연습 서버는 5초 뒤 504를 돌려주고 콘솔에 힌트를 남깁니다. 그다음 fetch('/api/slow', { signal: AbortSignal.timeout(2000) })처럼 브라우저 쪽에서 먼저 끊어 보세요. 11주차의 AbortController가 여기서 쓰입니다.

BaaS: 여러 사람이 같이 쓰는 데이터를 가장 빨리 얻는 길

함수를 쓰더라도 데이터는 어딘가에 두어야 합니다. BaaS는 데이터베이스·인증·파일 저장·호스팅을 콘솔에서 만들어 주고, 브라우저에서 바로 부르게 해 줍니다.

이 수업에서는 두 가지 이름만 기억하면 됩니다.

Supabase
PostgreSQL 데이터베이스 위에 자동 REST API, 인증, 파일 저장, 실시간 구독을 얹은 서비스입니다. 표(테이블)를 콘솔에서 만들면 바로 supabase.from('memos').select()로 읽을 수 있습니다.
Firebase
Google의 BaaS입니다. 인증·Firestore(문서형 DB)·Hosting을 한 콘솔에서 제공합니다. npm install firebase 뒤 initializeApp(firebaseConfig)로 시작합니다.

키 구분: 브라우저에 둘 수 있는 키와 없는 키

BaaS를 브라우저에서 직접 부른다는 말은, 키가 브라우저 코드 안에 들어간다는 뜻입니다. 그래서 키의 종류를 정확히 알아야 합니다.

키의 종류와 자리
키어디에 두나무엇을 하나
Supabase publishable key
sb_publishable_…		브라우저에 두어도 됩니다누구나 읽을 수 있는 키입니다. 그래서 RLS가 허용한 만큼만 할 수 있습니다. 공식 문구: "Anyone can read it, so it only reaches what Row Level Security allows."

예전 이름 anon · service_role각각 위 두 키의 "Legacy version"AI가 이 이름으로 코드를 주면 publishable·secret으로 바꿔 읽습니다. 2026년 말까지 폐기 예정이라고 안내되어 있습니다.
Firebase 웹 설정값 (apiKey 등)브라우저에 두어도 됩니다공개되어도 되는 식별자입니다. 접근 제어는 키가 아니라 보안 규칙이 합니다.

secret key가 브라우저 코드에 한 번이라도 들어가면, 그 페이지를 연 모든 사람이 우리 팀 데이터베이스 전체를 읽고 지울 수 있습니다. GitHub에 올린 뒤 지워도 커밋 기록에 남습니다. 그런 일이 생기면 콘솔에서 키를 새로 발급(회전)하고, 옛 키를 끕니다.

RLS: 테이블마다 "누가 어떤 행을" 규칙 켜기

Row Level Security는 데이터베이스가 행 단위로 읽기·쓰기를 허용하는 규칙입니다. publishable key가 안전한 이유는 이 규칙이 있기 때문입니다. 규칙이 없는 테이블은 누구나 모든 행을 읽고 지울 수 있습니다. 그러니 테이블을 만들면 RLS를 켜고, 정책을 하나 이상 씁니다. 메모 앱이라면 이런 두 줄짜리 뜻입니다.

읽기
모두 허용. 팀원 셋이 같은 목록을 보는 장면에 맞습니다.
쓰기
로그인한 사용자만, 그리고 자기 메모만. 처음에는 "본문이 비어 있지 않을 것"처럼 단순한 조건부터 시작해도 됩니다.

정책은 SQL로 씁니다. 정확한 문법은 공식 문서의 RLS 항목에서 복사하고, AI가 준 정책은 콘솔의 정책 편집 화면에서 "누가·어떤 행을·무엇을" 세 칸이 맞는지 읽어 봅니다.

Supabase 호출 코드 읽기

공식 문서의 최소 예를 메모 앱에 맞춰 옮긴 것입니다. 세 줄이 전부입니다. 클라이언트를 하나 만들고, 테이블을 고르고, 읽거나 씁니다. 결과는 늘 { data, error } 두 칸으로 옵니다.

import { createClient } from '@supabase/supabase-js'
// 번들러 없이 브라우저에서 바로 쓸 때:
// import { createClient } from 'https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/+esm'

// 프로젝트 URL과 publishable key는 콘솔의 API 설정에 있습니다. secret key는 여기 넣지 않습니다.
const supabase = createClient('https://<프로젝트>.supabase.co', '<publishable key>')

// 읽기: 테이블 전체, 또는 특정 열과 조건
const { data, error } = await supabase.from('memos').select()
const { data: study } = await supabase.from('memos').select('text').eq('tag', '공부')

// 쓰기: 한 행 넣기, 넣은 행 돌려받기
const { data: inserted, error: insertError } = await supabase
  .from('memos')
  .insert({ text: 'RLS 정책 읽기', tag: '공부' })
  .select()

읽을 때 눈에 둘 것 두 가지입니다. 첫째, error를 매번 확인합니다. RLS가 거절해도 예외가 아니라 error로 옵니다. 둘째, <프로젝트>와 <publishable key> 자리에 들어갈 값은 콘솔에서 복사하고, README에는 값이 아니라 "어디서 받는지"만 적습니다.

실습 2 · Supabase 모양으로 읽고 쓰기

실제 라이브러리는 인터넷과 진짜 프로젝트가 필요하므로, 여기서는 같은 모양의 연습용 stand-in을 씁니다. JS 탭 위쪽의 createClient는 흉내이고, 가운데 줄 아래부터가 여러분이 실제로 쓰게 될 코드입니다. 서버 탭은 Supabase의 자동 REST API와 정책을 아주 작게 흉내 냅니다. 서버 탭의 TODO를 채우면 마지막 테스트가 통과합니다.

해 볼 것: 서버 탭에서 withKey 호출을 지워 보세요. 키 없이도 읽힙니다. 실제 Supabase에서는 RLS를 끈 테이블이 이런 상태입니다.

비밀 관리: 키는 코드가 아니라 환경에 둡니다

내부 동작
브라우저로 보낸 JS는 전부 공개입니다. 난독화해도 Network 탭과 소스 보기에 그대로 보입니다. 서버리스 플랫폼은 배포할 때 넣어 둔 값을 실행 시점에 함수에 주입합니다. Workers는 env.KEY, Vercel·Netlify는 process.env.KEY로 읽습니다. 값은 저장소에 없고 플랫폼의 저장소에만 있습니다. 로컬에서는 .env 파일을 쓰되 .gitignore에 넣습니다.
명세·문서
Supabase · API keys · 세 플랫폼의 비밀 값 넣기: wrangler secret put · vercel env · Netlify 화면(Netlify Functions · Get started)
트레이드오프
키를 숨기려면 브라우저 → 함수 → 외부 API로 한 겹이 늘어납니다. 지연과 함수 호출 수가 늘고, 함수 쪽에서 사용자별 호출 제한(rate limit)을 따로 생각해야 합니다. 대신 키가 새면 함수 한 곳만 고치면 됩니다. publishable key처럼 "공개 전제 + 규칙으로 제한"하는 키는 이 겹이 필요 없습니다.
5분 실험
실습 1의 서버 탭에 app.get('/api/secret-check', (req, res) => res.json({ has: Boolean(process.env.MY_SECRET) }))를 더합니다. 연습 서버에는 환경 변수가 없으니 false가 옵니다. 이제 JS 탭에서 console.log(process.env.MY_SECRET)을 써 보세요. ReferenceError가 납니다. 브라우저 코드에는 process.env가 없습니다. 그래서 "키는 서버 탭 쪽에만 있을 수 있다"는 것이 코드로 보입니다.

실시간 구독: 다른 사람이 쓴 메모가 내 화면에 나타나기까지

"팀원이 메모를 추가하면 내 화면도 바로 바뀐다"는 장면은 BaaS의 실시간 기능으로 얻습니다. 새로고침 없이, 서버가 먼저 알려 줍니다.

11주차까지의 흐름은 "내가 물어본다(fetch) → 서버가 답한다"였습니다. 실시간 구독은 방향이 반대입니다. 한 번 구독해 두면, 테이블에 행이 들어올 때 서버가 브라우저에 밀어 줍니다. 7주차 특강에 나온 WebSocket이 그 밑에 있습니다. 아래는 supabase-js의 구독 코드를 메모 앱에 맞춘 읽기용 예입니다.

const channel = supabase
  .channel('memos-changes')                       // 구독 이름(아무 문자열)
  .on('postgres_changes',                         // 테이블 변경을 받겠다
      { event: 'INSERT', schema: 'public', table: 'memos' },
      (payload) => {
        addToList(payload.new);                   // payload.new = 새로 들어온 행
      })
  .subscribe();

// 화면을 떠날 때
// supabase.removeChannel(channel);

수업 직전 확인

실시간 구독 함수의 정확한 이름과, 테이블마다 실시간을 켜는 설정 위치는 Supabase 공식 문서의 Realtime 항목에서 다시 확인합니다. 위 코드는 읽는 연습용이며, 실제로 붙일 때는 공식 문서의 예를 복사합니다.

구독 코드를 읽을 때 세 가지만 찾으면 됩니다. 무엇을 구독하나(table·event), 왔을 때 무엇을 하나(콜백), 언제 끊나(removeChannel). 끊지 않으면 화면을 바꿀 때마다 구독이 쌓입니다.

실습 3 · 구독의 모양 흉내 내기

진짜 실시간은 WebSocket으로 서버가 먼저 알려 줍니다. 연습 서버에는 WebSocket이 없으니, 0.7초마다 물어보는 방식(폴링)으로 "알림이 오면 콜백이 돈다"는 모양만 흉내 냅니다. 버튼은 "다른 팀원이 자기 브라우저에서 메모를 썼다"를 대신합니다.

해 볼 것: 버튼을 세 번 누르고 네트워크 탭을 보세요. 폴링은 아무 일이 없어도 0.7초마다 요청을 보냅니다. 실제 WebSocket 구독은 바뀔 때만 데이터가 오갑니다. 이 차이가 "실시간을 BaaS에 맡기는 이유"입니다.

실제 프로젝트에 붙이는 순서

결정표(08)가 "채택"으로 끝났을 때만 시작합니다. 화면은 GitHub Pages에 그대로 두고, 저장과 키만 바깥으로 보냅니다.

  1. 범위를 한 줄로 적기"★ 단계에서 메모를 저장하고, 팀원 셋이 같은 목록을 본다." 이 한 줄에 없는 기능은 이번에 붙이지 않습니다.
  2. 데이터를 먼저 만들기Supabase 콘솔에서 프로젝트 → 테이블(memos: id, text, tag, created_at) → RLS 켜기 → 정책 쓰기. 표가 팀 시트 ⑦의 "남기는 것"과 같은지 봅니다.
  3. 브라우저에서 읽기부터createClient + select()로 목록을 그립니다. 쓰기는 그다음입니다. 한 번에 둘 다 하지 않습니다.
  4. 키가 필요하면 함수 한 개외부 API 키는 함수(/api/translate 같은 경로 하나)에만 둡니다. 브라우저는 함수를 부르고, 함수가 키를 붙여 외부 API를 부릅니다.
  5. README에 실행 방법과 변수 이름 적기값은 적지 않고 이름만(SUPABASE_URL, API_KEY) 적습니다. 어디서 받는지, 누가 가지고 있는지도 한 줄 남깁니다.

$ npm install @supabase/supabase-js
import { createClient } from 'https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/+esm'

$ cd my-first-worker

$ npx wrangler deploy              # *.workers.dev 주소로 배포

AI에게 맡길 일, 직접 판단할 일

이번 모듈의 AI 단계는 Delegate → Inspect입니다. 코드 초안은 맡기고, 키의 자리와 규칙은 우리가 봅니다.

  3. 무료 한도 중 우리 시연에서 먼저 닿을 것이 무엇인지 알고 있나요?

잠든 프로젝트

공급자 종속
BaaS의 인증·실시간·정책은 그 서비스 안에서만 그대로 돌아갑니다. 다른 곳으로 옮기려면 데이터를 내보내고 코드를 다시 씁니다. 수업 프로젝트에서는 감수할 만하지만, 결정표의 "대안" 칸에 "옮길 때 무엇을 다시 쓰나"를 한 줄 적어 둡니다. 함수 쪽은 세 플랫폼 모두 Web 표준 Request·Response 모양을 쓰므로 비교적 옮기기 쉽습니다.
첫 요청의 지연
