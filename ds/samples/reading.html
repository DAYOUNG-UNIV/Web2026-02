웹은 요청과 응답

브라우저와 서버는 정해진 형식의 편지를 주고받습니다. 편지 봉투(URL·메서드·헤더)와 내용물(본문)을 나누어 읽는 법을 익힙니다.

URL 읽기

주소창의 URL은 "어느 서버의, 어떤 자원을, 어떤 조건으로" 달라는 요청을 한 줄로 적은 것입니다. 물음표 뒤의 쿼리 문자열은 같은 자원을 다른 조건으로 요청할 때 씁니다.

https://api.example.kr:443/v1/works?q=빛&page=2#top
URL을 이루는 부분
부분예뜻
프로토콜https어떤 규칙으로 주고받을지. 암호화된 HTTP입니다.
호스트api.example.kr요청을 받을 서버의 이름.
포트443서버 안의 문 번호. https는 보통 생략합니다.
경로/v1/works서버 안에서 원하는 자원의 위치.
쿼리q=빛&page=2요청의 조건. &로 여러 개를 잇습니다.
조각#top페이지 안의 위치. 서버로는 보내지지 않습니다.

HTTP 메서드

같은 경로라도 메서드가 다르면 다른 요청입니다. 팀 프로젝트에서 자주 쓰는 네 가지만 기억하면 충분합니다.

GET
자원을 읽습니다. 본문 없이 보내고, 몇 번을 보내도 서버의 데이터가 바뀌지 않아야 합니다.
POST
새 자원을 만듭니다. 만들 내용을 본문에 JSON으로 담아 보냅니다.
PUT · PATCH
있는 자원을 고칩니다. PUT은 통째로 바꾸고, PATCH는 일부만 바꿉니다.
DELETE
자원을 지웁니다. 되돌릴 수 없으니 화면에서 한 번 더 묻습니다.

상태 코드

상태 코드는 첫 자리만 보아도 절반은 읽힙니다. 2는 성공, 4는 요청한 쪽의 문제, 5는 서버의 문제입니다.

서버는 응답의 첫 줄에 세 자리 숫자로 결과를 알려 줍니다. 화면에 무엇을 보여 줄지는 이 숫자를 보고 정합니다. 특히 404와 500은 사용자에게 다른 문장으로 안내해야 합니다.

팀 프로젝트에서 자주 만나는 상태 코드
코드이름화면에서 할 일
200OK받은 데이터를 그립니다.
201Created"저장했습니다"를 알리고 목록에 더합니다.
400Bad Request입력 칸 옆에 무엇이 잘못되었는지 보여 줍니다.
401Unauthorized다시 로그인하도록 안내합니다.
404Not Found"찾는 항목이 없습니다"와 돌아갈 길을 보여 줍니다.
500Internal Server Error"잠시 후 다시 시도"와 다시 시도 버튼을 둡니다.

헤더와 본문, 그리고 JSON

응답은 헤더와 본문으로 나뉩니다. 헤더의 Content-Type이 application/json이면 본문은 JSON입니다. JSON은 JavaScript 객체와 닮았지만 규칙이 더 엄격합니다.

[
  { "id": 1, "title": "소리 지도", "team": "1팀", "tags": ["소리", "지도"] },
  { "id": 2, "title": "빛의 시간표", "team": "3팀", "tags": [] }
]

JSON은 JavaScript 객체가 아닙니다

키는 반드시 큰따옴표로 감싸고, 마지막 항목 뒤에 쉼표를 두지 않으며, 주석을 쓸 수 없습니다. 하나라도 어기면 JSON.parse와 res.json()이 SyntaxError를 냅니다.

개발자 도구 Network 탭 읽기

코드가 요청을 제대로 보냈는지는 추측하지 말고 Network 탭에서 확인합니다. Windows에서는 F12, macOS에서는 ⌥ ⌘ I로 개발자 도구를 엽니다.

  1. Network 탭 열기열어 둔 뒤에 새로고침해야 기록이 남습니다.
  2. Fetch/XHR만 보기이미지와 글꼴을 걸러 내면 API 요청만 남습니다.
  3. 요청 한 줄 누르기Headers에서 메서드와 상태 코드를 봅니다.
  4. Response 읽기서버가 실제로 보낸 JSON을 확인합니다.

아래 실습은 실제 인터넷 대신 이 페이지 안의 연습용 서버에 요청합니다. 서버 탭의 코드가 응답을 만들고, 결과 아래의 네트워크 탭이 개발자 도구의 Network 탭 역할을 합니다.

해 볼 것: JS의 '/api/works'를 '/api/works/2'로 바꾸어 실행해 보세요. 응답이 배열이 아니라 객체 하나이므로 for…of에서 오류가 납니다. 콘솔의 오류 문장과 네트워크 탭의 응답 본문을 나란히 놓고 읽어 보세요.

REST 방식으로 자원 이름 짓기

경로에는 동사 대신 명사(자원)를 쓰고, 무엇을 할지는 메서드로 나타내는 방식을 REST라고 부릅니다. 팀 프로젝트의 API를 설계할 때 이 규칙을 따르면 문서 없이도 읽기 쉬운 주소가 됩니다.

같은 자원, 다른 메서드
요청뜻

GET /api/works/33번 작품 하나
POST /api/works작품 하나 추가
PATCH /api/works/33번 작품 일부 수정

/api/getWorks나 /api/deleteWork?id=3처럼 경로에 동사를 넣는 방식은 피합니다. 캐시와 권한 설정이 메서드를 기준으로 동작하기 때문입니다.

비동기와 fetch

서버의 답은 언제 올지 모릅니다. 기다리는 동안에도 화면이 멈추지 않게 하는 방법과, 답이 오지 않거나 틀렸을 때 사용자에게 알리는 방법을 배웁니다.

기다리는 동안 멈추지 않기

식당에서 주문한 뒤 진동벨을 받고 자리로 돌아가는 것처럼, 비동기 코드는 요청을 보내고 바로 다음 줄로 넘어갑니다. fetch는 결과 대신 "나중에 결과를 주겠다는 약속", 곧 Promise를 돌려줍니다.

  1. fetch(url) 호출요청을 보내고 Promise를 바로 돌려받습니다. 화면은 계속 움직입니다.
  2. 응답 헤더 도착Promise가 Response 객체로 이행됩니다. 본문은 아직 읽지 않았습니다.
  3. res.json() 호출본문을 끝까지 읽고 JSON을 해석하는 두 번째 Promise입니다.
  4. 데이터로 화면 그리기9주차의 render(state)에 받은 데이터를 넘깁니다.

Promise에서 async/await로

같은 일을 두 가지 문법으로 쓸 수 있습니다. 이 수업에서는 위에서 아래로 읽히는 async/await를 기본으로 씁니다. AI가 then으로 쓴 코드를 주더라도 읽을 수 있도록 둘 다 봐 둡니다.

async function loadWorks() {
  const res = await fetch('/api/works');
  const works = await res.json();
  render(works);
}

await는 async 함수 안에서만 쓸 수 있습니다. 함수 밖 맨 위에서 쓰려면 <script type="module">이 필요합니다.

function loadWorks() {
  return fetch('/api/works')
    .then((res) => res.json())
    .then((works) => render(works));
}

then은 앞의 Promise가 이행되면 실행할 함수를 등록합니다. 단계마다 들여쓰기가 깊어지지 않도록 사슬처럼 이어 씁니다.

fetch는 404에도 실패하지 않는다

fetch의 Promise가 거부되는 것은 네트워크가 끊겼거나 요청 자체를 보낼 수 없을 때뿐입니다. 서버가 404나 500으로 답했다면 그것도 "응답을 받은 것"이므로 Promise는 정상으로 이행됩니다. 그래서 res.ok를 직접 검사해야 합니다.

const res = await fetch(url);
const works = await res.json();
render(works); // 404여도 여기까지 옵니다
const res = await fetch(url);
if (!res.ok) {
  throw new Error('서버 응답 ' + res.status);
}
const works = await res.json();
render(works);

try/catch만 두르고 res.ok 검사를 빼면, 404 응답의 본문({"error": "…"})이 목록 자리에 들어가 엉뚱한 곳에서 TypeError가 납니다. 오류 문장이 원인과 멀어져서 찾기 어렵습니다.

로딩·빈 목록·오류: 세 가지 상태

데이터를 가져오는 화면은 적어도 세 가지 상태를 가집니다. 기다리는 중, 받았지만 비어 있음, 받지 못함. 세 상태 모두에 사용자가 읽을 문장이 있어야 합니다.

아래 실습에는 자동 테스트가 붙어 있습니다. 처음 실행하면 세 테스트 중 두 개만 통과합니다. JS의 TODO 줄을 고쳐서 모두 통과시켜 보세요.

결과 아래 네트워크 탭의 지연을 3초로 바꾸고 다시 실행하면 로딩 상태를 눈으로 볼 수 있습니다. 오프라인을 켜면 fetch가 거부되는 경우, 곧 catch로 가는 경우를 만들 수 있습니다.

이벤트 루프와 마이크로태스크: 출력 순서 맞히기

브라우저는 한 번에 한 가지 일만 합니다. 지금 하던 코드를 끝까지 실행한 뒤, 기다리던 일 가운데 Promise의 후속 작업(마이크로태스크)을 먼저 처리하고, 그다음에 setTimeout 같은 작업(태스크)을 처리합니다.

console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// 출력: A D C B

setTimeout(…, 0)이 "바로"가 아니라 "지금 일과 밀린 Promise 작업이 모두 끝난 뒤"라는 점이 핵심입니다.

여러 요청을 한꺼번에: Promise.all과 AbortController

서로 기다릴 필요가 없는 요청은 동시에 보내고 모두 끝나기를 기다립니다. 하나라도 실패하면 전체가 거부된다는 점에 주의합니다.

const [works, teams] = await Promise.all([
  fetch('/api/works').then((r) => r.json()),
  fetch('/api/teams').then((r) => r.json())
]);

검색창에 빠르게 입력하면 앞선 요청의 답이 늦게 도착해 최신 결과를 덮어쓸 수 있습니다. 새 요청을 보낼 때 이전 요청을 취소하면 이 문제를 피할 수 있습니다.

let controller;
async function search(q) {
  controller?.abort();
  controller = new AbortController();
  const res = await fetch('/api/works?q=' + q, { signal: controller.signal });
  render(await res.json());
}

데이터 저장

서버 없이도 이 브라우저 안에는 데이터를 남길 수 있습니다. 무엇을 저장해도 되는지, 언제 서버가 필요한지도 함께 판단합니다.

localStorage에 JSON으로 저장하기

localStorage는 문자열만 저장합니다. 배열이나 객체는 JSON.stringify로 문자열로 바꾸어 넣고, 꺼낼 때 JSON.parse로 되돌립니다.

const KEY = 'memos-v1';

export function saveMemos(memos) {
  localStorage.setItem(KEY, JSON.stringify(memos));
}

export function loadMemos() {
  try {
    return JSON.parse(localStorage.getItem(KEY)) ?? [];
  } catch {
    return []; // 저장된 값이 깨졌으면 빈 목록으로 시작
  }
}

localStorage는 같은 컴퓨터를 쓰는 사람 누구나 개발자 도구로 읽을 수 있습니다. 비밀번호, 학번, 연락처, API 키는 저장하지 않습니다. 저장 키 이름에 -v1처럼 버전을 붙여 두면 데이터 모양을 바꿀 때 옛 데이터와 섞이지 않습니다.

9주차 메모 앱에 저장 더하기

메모를 몇 개 추가한 뒤 실행을 다시 눌러 보세요. 새로고침과 같은 효과입니다. 메모가 남아 있으면 저장과 복원이 모두 동작하는 것입니다. 연습 화면의 저장소는 이 페이지를 닫으면 비워지고, 처음 코드로를 눌러도 비워집니다.

서버가 필요한 순간

localStorage는 "이 브라우저, 이 사람"만 봅니다. 아래 가운데 하나라도 해당하면 서버나 서비스형 백엔드가 필요합니다. 팀에서 필요하다고 판단했다면 선택 모듈을 함께 보세요.

결과 검토 체크

AI가 만든 코드를 "돌아가니까 됐다"로 끝내지 않습니다. 아래 다섯 가지를 확인한 뒤 팀 PR에 올리고, 확인한 내용을 AI USE NOTE에 적습니다.

외부 API · 키 · CORS

날씨, 지도, 전시 정보처럼 다른 회사의 API를 쓰고 싶을 때 먼저 확인할 세 가지입니다.

API 키는 브라우저 코드에 두지 않는다

브라우저에서 실행되는 코드는 누구나 볼 수 있습니다. GitHub Pages에 올린 JS 파일에 키를 적으면, 키가 공개된 것과 같습니다. 키가 필요한 API는 서버를 거쳐 부르고, 키는 서버의 환경 변수에 둡니다.

  • team-app
    • index.html
    • src
      • app.js/api/weather 만 부릅니다
    • server
      • index.js키를 붙여 외부 API를 대신 부릅니다
    • .env키 보관 · 저장소에 올리지 않습니다
    • .gitignore.env 한 줄이 들어 있어야 합니다

키를 실수로 커밋했다면 파일에서 지우는 것만으로는 부족합니다. 커밋 기록에 남아 있기 때문입니다. 키를 발급한 서비스에서 바로 폐기하고 새 키를 받은 뒤, 강사에게 eTL 메시지로 알려 주세요.

CORS: 브라우저가 다른 출처의 응답을 막는 이유

브라우저는 https://team.github.io에서 실행된 코드가 https://api.other.kr의 응답을 읽으려 하면, 상대 서버가 허락했는지 응답 헤더 Access-Control-Allow-Origin을 확인합니다. 허락이 없으면 응답이 도착했어도 코드에 넘겨주지 않습니다. 콘솔에는 "blocked by CORS policy"가 찍힙니다.

이것은 우리 코드의 버그가 아니라 상대 서버의 설정입니다. 고치는 방법은 세 가지뿐입니다. 상대가 CORS를 허락하는 API를 고르거나, 우리 서버를 거쳐 부르거나, 해당 서비스가 제공하는 공식 SDK를 씁니다. 브라우저 확장 프로그램으로 CORS를 끄는 방법은 내 컴퓨터에서만 동작하므로 해결책이 아닙니다.

Q1서버가 404로 답했을 때 await fetch(url)는 어떻게 되나요?

  • 거부되는 것은 네트워크 오류처럼 응답을 아예 받지 못한 경우입니다.

  • 맞습니다. 404도 서버가 보낸 응답이므로 직접 res.ok를 검사해야 합니다.

  • 본문에 무엇이 있는지는 서버가 정합니다. 보통 오류를 설명하는 객체가 옵니다.

  • 개발자 도구로 누구나 읽을 수 있으므로 키는 서버에 둡니다.
