터미널과 npm

마우스로도 할 수 있는 일을 왜 글자로 할까요. 서버를 띄우고, 패키지를 쓰고, AI 에이전트를 부르는 일이 모두 터미널에서 시작되기 때문입니다. 명령 다섯 개면 충분합니다.

왜 터미널인가

이 절을 읽고 나면 터미널이 "어느 폴더에서, 어떤 프로그램을, 어떤 조건으로 실행할지"를 적는 창이라는 것을 설명할 수 있습니다.

터미널은 글자로 명령을 내리는 창입니다. 탐색기(Finder)에서 폴더를 더블클릭하는 일을 cd 한 줄로 하고, 프로그램 아이콘을 더블클릭하는 일을 프로그램 이름 한 줄로 합니다. 글자로 적으면 세 가지가 좋아집니다. 같은 일을 정확히 되풀이할 수 있고, 다른 사람에게 그대로 보낼 수 있고, AI 에이전트가 같은 명령을 실행할 수 있습니다.

이번 주에 터미널에서 할 일은 세 가지뿐입니다. 프로젝트 폴더로 들어가기, 로컬 서버 띄우기, 에이전트 실행하기. 세 가지 모두 "지금 어느 폴더에 있는가"가 중요합니다. 터미널 명령의 절반은 폴더 위치를 확인하고 옮기는 일입니다.

터미널 앱(응용 프로그램 › 유틸리티 › 터미널)을 엽니다. 기본 셸은 zsh입니다. VS Code 안에서는 메뉴 터미널 › 새 터미널(단축키 ⌃ `)로 열면 현재 프로젝트 폴더에서 시작합니다.

Windows 터미널 또는 PowerShell을 엽니다. VS Code 안에서는 메뉴 터미널 › 새 터미널(단축키 Ctrl `)이 가장 편합니다. 이 교안의 명령은 PowerShell에서도 대부분 같은 이름으로 동작합니다(pwd, ls, cd, mkdir). 경로 구분자가 \라는 점만 다릅니다.

Node.js와 npm 확인·설치

이 절을 읽고 나면 Node.js가 왜 필요한지, 어떤 버전이면 되는지, 설치가 됐는지 어떻게 확인하는지 알 수 있습니다.

Node.js는 브라우저 밖에서 JavaScript를 실행하는 프로그램입니다. 우리가 직접 Node로 서버를 짜지는 않습니다. 하지만 로컬 서버 도구(serve), 테스트 도구(Vitest), AI 에이전트(npm으로 설치할 때)가 모두 Node 위에서 돕니다. npm은 Node와 함께 설치되는 패키지 관리자입니다.

이 수업의 기준은 Node 22.12 이상이고, 새로 설치한다면 Node 24 LTS를 권장합니다. 11~13주차에 쓸 도구들(Vite, Vitest, Lighthouse, supabase-js)이 모두 22.12 이상을 요구하기 때문입니다. LTS는 장기 지원 버전이라는 뜻입니다.

nodejs.org 다운로드 페이지가 안내하는 nvm 방식입니다. 터미널에 한 줄씩 붙여 넣습니다. 두 번째 줄은 터미널을 다시 열지 않고 nvm을 바로 쓰기 위한 것입니다.

$ curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh | bash
$ \. "$HOME/.nvm/nvm.sh"
$ nvm install 24
$ node -v
v24.22.1
$ npm -v

설치 파일(.pkg)을 내려받아 더블클릭해도 됩니다. 어느 쪽이든 설치 뒤에는 터미널을 새로 열어 node -v를 확인합니다.

nodejs.org 다운로드 페이지에서 Windows용 설치 파일(.msi)을 내려받아 실행합니다. 설치 마법사는 기본값 그대로 다음을 누르면 됩니다. 끝나면 PowerShell을 새로 열어 확인합니다.

package.json · scripts · npx

이 절을 읽고 나면 npm run dev가 무엇을 실행하는지 package.json에서 찾아 읽을 수 있습니다.

프로젝트 폴더 맨 위의 package.json은 "이 프로젝트의 이름과 실행 방법"을 적은 파일입니다. 그중 scripts 칸이 핵심입니다. npm run 이름을 치면 npm이 이 칸에서 이름을 찾아 오른쪽 명령을 실행합니다. 긴 명령에 짧은 이름을 붙여 두는 것입니다. 팀원과 AI 에이전트가 같은 이름으로 같은 일을 할 수 있습니다.

{
  "name": "team-app",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "serve .",
    "test": "vitest run"
  }
}
npm run dev
scripts.dev에 적힌 serve .를 실행합니다. npm start와 npm test는 run을 생략할 수 있는 특별한 이름입니다.
pre·post
pretest가 있으면 test 앞에, posttest가 있으면 뒤에 자동으로 실행됩니다. 이름만으로 순서가 정해집니다.
npm install 이름
패키지를 node_modules/에 내려받고 package.json의 dependencies에 적습니다. 이번 주에는 설치할 패키지가 없습니다.
npx 이름
패키지를 설치하지 않고 한 번 실행합니다. 프로젝트의 node_modules/.bin에 있으면 그것을, 없으면 임시로 내려받아 실행합니다. 5주차의 npx @tailwindcss/cli가 그랬습니다.

아래 실습은 npm이 scripts를 읽는 규칙을 JavaScript로 흉내 낸 것입니다. 실제 npm을 실행하는 것은 아니지만, pre와 post의 순서를 눈으로 확인할 수 있습니다. 테스트 탭에서 실패하는 한 줄을 고쳐 보세요.

ESM과 CommonJS, 번들러가 하는 일, lock 파일

내부 동작

JavaScript 모듈 체계는 둘입니다. ESM(import/export)은 언어 표준이고 브라우저와 Node 모두 지원합니다. 가져오기가 정적이라(파일 맨 위, 이름이 고정) 엔진이 실행 전에 의존 관계 그래프를 만들 수 있고, 그래서 쓰지 않는 내보내기를 번들러가 지울 수 있습니다(tree shaking). CommonJS(require()/module.exports)는 Node의 옛 방식입니다. 함수 호출이라 실행 중에 아무 데서나 부를 수 있지만, 브라우저에는 require가 없습니다. package.json의 "type": "module"은 "이 프로젝트의 .js는 ESM이다"라는 선언입니다.

번들러(Vite가 내부에서 쓰는 Rollup·esbuild 등)는 모듈 수십 개를 파일 몇 개로 합치고, 안 쓰는 코드를 지우고, 옛 브라우저용 문법으로 바꿉니다. 이 수업의 기본 경로(HTML·CSS·JS 파일을 그대로 서빙)에는 번들러가 없습니다. 선택 모듈 react에서 Vite를 쓸 때 처음 만납니다.

package-lock.json은 npm install이 실제로 내려받은 모든 패키지의 정확한 버전을 적은 파일입니다. package.json의 ^4.6.1은 "4.6.1 이상 5 미만"이라는 범위이고, lock 파일은 그중 어느 것을 받았는지 고정합니다. 팀원 모두가 같은 버전을 받으려면 lock 파일을 커밋해야 합니다.

트레이드오프

번들러 없이 ESM을 브라우저에 직접 주면 설정이 없고 디버깅이 쉽지만, 모듈마다 요청이 하나씩 나가고 npm 패키지를 바로 import할 수 없습니다. 번들러를 쓰면 요청이 줄고 패키지를 자유롭게 쓰지만, 빌드 단계와 설정 파일이 생기고 "소스와 실제 실행 코드가 다르다"는 간접성이 생깁니다. 이 수업의 팀 프로젝트 크기라면 전자가 먼저입니다.

왜 서버를 띄우나 · file://와 http://

이 절을 읽고 나면 주소창이 file://로 시작할 때와 http://로 시작할 때 무엇이 다른지 설명할 수 있습니다.

2주차에 HTML 파일을 더블클릭하면 주소가 file:///C:/Users/…/index.html처럼 보인다는 것을 봤습니다(2주차 08). 이때 브라우저는 서버 없이 내 디스크의 파일을 직접 읽습니다. 화면만 볼 때는 충분하지만, 세 가지가 막힙니다.

  • fetch('data/notes.json')가 실패합니다. 브라우저는 file:// 페이지에 '출처(origin)'를 주지 않아 다른 파일을 요청하지 못하게 막습니다. 11주차에 데이터를 가져오는 코드는 전부 이 영향을 받습니다.
  • <script type="module">이 같은 이유로 막힙니다.
  • 배포(GitHub Pages)와 조건이 다릅니다. 배포된 사이트는 https://로 열립니다. 내 컴퓨터에서도 같은 조건으로 봐야 "배포하니 안 되네"를 미리 잡습니다.

로컬 서버는 내 컴퓨터 안에서 도는 작은 웹 서버입니다. 주소 http://localhost:3000/index.html의 localhost는 "이 컴퓨터", 3000은 서버가 기다리는 문 번호(포트)입니다. 브라우저는 이 주소로 요청을 보내고, 서버는 폴더의 파일을 응답으로 돌려줍니다. 서버의 종류로 말하면, 이 서버는 요청마다 코드를 실행하지 않고 파일을 그대로 돌려주는 정적 서버입니다.

연습 · 서버 띄우기

프로젝트 폴더에 들어가 Node 버전을 확인하고 서버를 띄우는 순서입니다. 실제 터미널에서는 서버가 켜진 뒤 브라우저에서 주소를 열고, Network 탭을 연 채 새로고침합니다.

Network 탭 읽기

이 절을 읽고 나면 Network 탭의 한 줄을 골라 메서드, 상태 코드, 응답 종류를 읽을 수 있습니다.

개발자 도구의 Network 탭은 이 페이지가 보낸 모든 요청과 받은 응답의 기록입니다. 5주차에 Console 탭을 봤다면 그 옆 탭입니다. 기록은 탭을 연 뒤부터 남으므로 열고 나서 새로고침해야 합니다.

  1. Network 탭 열기개발자 도구에서 Network. 열어 둔 뒤 새로고침합니다.
  2. 요청 한 줄 누르기Headers에서 요청 URL, 메서드, 상태 코드를 봅니다.
  3. Response 보기서버가 돌려준 본문. HTML이면 HTML, JSON이면 JSON.
  4. 없는 주소 요청빨간 줄과 404. 서버는 살아 있고 파일만 없습니다.

내부 동작

브라우저는 받은 응답을 저장해 두고(캐시), 같은 URL을 다시 요청할 때 서버에 안 가고 사본을 쓰기도 합니다. 규칙은 응답 헤더가 정합니다. Cache-Control: max-age=3600이면 한 시간 동안은 서버에 묻지도 않습니다. no-cache이면 쓰기 전에 "바뀌었나요?"라고 묻습니다. 그 물음이 조건부 요청입니다. 서버가 응답에 지문 ETag: "v1"을 붙여 주면, 브라우저는 다음 요청에 If-None-Match: "v1"을 넣어 보냅니다. 서버는 내용이 같으면 본문 없이 304 Not Modified만 돌려주고, 브라우저는 가진 사본을 씁니다. 전송량이 0에 가까워집니다.

"배포했는데 안 바뀜"은 보통 브라우저가 옛 사본을 쓰고 있는 것입니다. 강력 새로고침은 캐시를 무시하고 다시 받습니다. GitHub Pages는 짧은 max-age를 주지만 반영 자체에 최대 10분이 걸릴 수 있습니다. 둘을 구분해야 합니다. Network 탭에서 상태가 200인데 내용이 옛것이면 배포 지연, 304나 "(memory cache)"이면 내 캐시입니다.

명세·공식 문서
  • MDN · HTTP 상태 코드(304 포함): developer.mozilla.org/…/HTTP/Reference/Status
  • MDN · HTTP caching 가이드: developer.mozilla.org/…/HTTP/Guides/Caching
트레이드오프

캐시를 길게 잡으면(max-age 큼) 빠르고 서버 부담이 적지만 수정이 늦게 보입니다. 짧게 잡거나 no-cache로 두면 늘 최신이지만 요청마다 왕복이 생깁니다. 실무의 절충은 "파일 이름에 지문을 넣고(app.3f2a.js) 길게 캐시, HTML만 짧게"입니다. 번들러가 이 이름을 자동으로 만들어 줍니다.

5분 실험

같은 파일을 두 번 요청합니다. 첫 응답은 200과 ETag, 둘째 응답은 304입니다. 서버 탭의 tag를 "v2"로 바꾸고 다시 실행하면 둘째 요청도 200이 됩니다. 내용이 바뀌면 지문이 바뀌어야 캐시가 풀립니다.

왜 규칙이 필요한가

그래서 GitHub에 규칙을 설정으로 겁니다. 설정은 사람이 깜빡해도, 에이전트가 시도해도 지켜집니다. 이번 주 팀 저장소의 최소 규칙은 셋입니다.

  1. main은 PR로만직접 push는 거부됩니다. 룰셋 "Require a pull request before merging".
  2. 리뷰 1명자기 PR은 자기가 승인하지 않습니다. "Required approvals: 1".
  3. 지우기·강제 push 금지"Restrict deletions"와 "Block force pushes". 이력이 사라지지 않습니다.

OT의 GitHub 흐름 그대로입니다. Issue → Branch → AI 작업 → Diff·Test → Pull Request → Review·Merge. 이번 주에는 README 한 줄로 이 흐름을 한 바퀴 돕니다.

# 메모 분류
<<<<<<< HEAD
실행: npx serve .
=======
실행: npx serve src
>>>>>>> origin/main
빌드 없음

<<<<<<< HEAD부터 =======까지가 내 버전, 그 아래 >>>>>>>까지가 상대 버전입니다. 셋 중 하나를 고릅니다. 내 것, 상대 것, 둘을 합친 새 문장. 고른 뒤 표시 줄 세 개를 반드시 지웁니다.

아래 상자는 선택입니다. Git을 조금 아는 분이 "왜 같은 줄만 충돌인가"와 "이력을 어떻게 읽기 쉽게 두나"를 더 보는 내용입니다.

rebase와 merge, Conventional Commits, CODEOWNERS, squash merge

내부 동작

Git의 병합은 3-way merge입니다. 두 브랜치의 공통 조상(base)과 양쪽(ours, theirs)을 비교해, 한쪽만 바꾼 줄은 그 변경을 택하고, 양쪽이 같은 줄을 다르게 바꿨을 때만 충돌로 남깁니다. 줄 단위 비교이므로 "같은 파일"이 아니라 "같은 줄(과 그 주변)"이 기준입니다. git merge는 병합 커밋을 하나 만들어 두 갈래를 잇고, git rebase는 내 커밋들을 상대 브랜치 끝에 다시 쌓아 직선으로 만듭니다. 결과 파일은 같고 이력 모양이 다릅니다.

GitHub의 PR 병합 버튼에도 세 가지가 있습니다. Merge commit(이력 보존), Squash and merge(PR의 커밋 여러 개를 하나로 합쳐 main에 한 줄), Rebase and merge(직선). 팀 프로젝트처럼 "작은 커밋을 많이, PR 단위로 읽고 싶다"면 squash가 main 이력을 가장 읽기 쉽게 합니다. 단, squash 뒤에는 원래 브랜치의 커밋과 main의 커밋이 다른 것이 되므로, 병합된 브랜치는 지우고 새로 만듭니다.

Conventional Commits는 커밋 메시지 첫 줄의 약속입니다. <type>[scope]: <description>. feat:는 새 기능, fix:는 버그 수정, 그 밖에 docs: style: refactor: test: chore:. 파괴적 변경은 ! 또는 BREAKING CHANGE: 푸터. 수업용 최소 규칙은 "type(범위): 한 줄 설명, 한글 허용, 72자 이내"입니다. CODEOWNERS(.github/CODEOWNERS)는 "이 경로는 이 사람이 리뷰한다"를 적는 파일로, 룰셋의 "Require review from Code Owners"와 짝입니다. 다섯 명 팀에서는 docs/를 한 명이 맡는 정도면 충분합니다.

트레이드오프

rebase는 이력이 직선이라 읽기 쉽지만 커밋 해시가 바뀌므로 이미 push한 브랜치를 rebase하면 팀원과 어긋납니다("공유한 브랜치는 rebase하지 않는다"). merge는 안전하지만 병합 커밋이 쌓여 이력이 복잡해집니다. 학기 프로젝트의 절충은 "개인 브랜치는 자유, main 병합은 squash"입니다.

5분 실험

3-way merge를 줄 단위로 흉내 낸 코드입니다. 팀원 1은 3번째 줄, 팀원 2는 2번째 줄을 고쳤으므로 자동 병합됩니다. theirs의 3번째 줄도 바꿔 보세요. 같은 줄을 다르게 고치는 순간 충돌 표시가 생깁니다. 같은 줄을 같게 고치면 어떻게 되는지도 확인해 보세요.

AI 코딩 에이전트 시작하기

채팅창에 코드를 붙여 넣던 방식에서, 에이전트가 내 저장소를 직접 읽고 고치는 방식으로 넘어갑니다. 도구는 셋 중 하나면 됩니다. 중요한 것은 도구가 아니라 "사람이 확인하는 지점"을 어디에 두느냐입니다.

공통 원리 한 장

이 절을 읽고 나면 어떤 에이전트든 네 단계로 돈다는 것과, 사람이 끼어드는 지점이 어디인지 말할 수 있습니다.

코딩 에이전트는 프로젝트 폴더에서 실행되는 프로그램입니다. 요청을 받으면 파일을 읽고, 파일을 바꾸고, 명령을 실행하고, 결과를 보고 다시 읽습니다. 그 사이사이에 사람이 확인합니다. Claude Code 문서는 이 반복을 "gather context → take action → verify results"라고 부르고, 모델을 둘러싼 이 층을 agentic harness라고 부릅니다. OT에서 들은 '하네스'라는 말이 바로 이것입니다.

  1. 읽는다AGENTS.md·CLAUDE.md, 요청한 파일, 폴더 구조
  2. 바꾼다파일 편집. 바꾸기 전에 diff를 보여 주고 묻습니다.
  3. 실행한다테스트·서버·git 명령. 실행 전에 묻습니다.
  4. 사람이 확인한다권한 프롬프트에 답하고, diff를 읽고, 결과를 직접 봅니다.

Codex와 Claude Code는 이름이 다를 뿐 같은 구조입니다. (1) 프로젝트 폴더에서 실행하고, (2) 지시 파일(AGENTS.md 또는 CLAUDE.md)을 먼저 읽고, (3) 읽기는 자유지만 편집·명령·네트워크는 권한 모드에 따라 묻고, (4) diff를 사람이 확인하고, (5) git으로 되돌릴 수 있게 둡니다. ChatGPT Edu 웹에서 파일을 붙여 넣고 제안을 받아 내가 적용하는 방식도 같은 흐름을 손으로 하는 것입니다.

세 경로 중 하나면 됩니다

이 수업은 특정 유료 도구를 전제하지 않습니다. 유료 여부가 성적 차이로 이어지지 않습니다. 아래 셋 중 지금 되는 것 하나로 과제를 하면 됩니다. 수업의 라이브 데모는 한 가지 도구로 하고, 나머지는 AI 실습 매뉴얼의 대응표로 따라갈 수 있습니다.

최근 버전(v2.1.283 이후)은 터미널에서 auto 모드로 시작합니다. 분류기가 사람 대신 승인하는 모드입니다. 수업에서는 Shift Tab을 눌러 상태 표시줄이 ⏸ manual mode on이 되게 하고 시작합니다. 설정으로 고정하려면 ~/.claude/settings.json에 "permissions": { "defaultMode": "default" }.

/diff로 작업 트리의 변경을 봅니다. /rewind(또는 Esc Esc)는 프롬프트 단위 체크포인트로 코드·대화를 되돌립니다. 영구 기록은 git입니다.
컨텍스트와 비용
/clear는 새 대화, /compact는 요약해 비우기, /context는 무엇이 차지하는지, /usage(별칭 /cost)는 플랜 한도와 세션 비용. 매 요청마다 대화 전체를 다시 보내므로 긴 세션은 한 줄 질문도 비쌉니다.
쓰지 않을 것
--dangerously-skip-permissions는 "사람이 확인하는 지점"을 전부 없앱니다. 문서도 "격리된 컨테이너·VM에서만" 쓰라고 합니다. 수업 노트북에서는 쓰지 않습니다(OT 금지선: 무조건적 에이전트 권한).

설치 없이 지금 바로 할 수 있는 경로입니다. 흐름은 같습니다. 요청 → 변경 제안 → 내가 적용 → 확인. 에이전트가 해 주던 "읽기·바꾸기·실행"을 내가 손으로 하므로, 권한 프롬프트 대신 내 판단이 들어갑니다.

  1. 프로젝트 만들기사이드바의 프로젝트에 팀 이름으로 하나 만들고, docs/requirements.md와 AGENTS.md를 파일로 올립니다. 9주차에 만든 프로젝트를 이어 써도 됩니다.
  2. 요청에 범위 적기"README.md의 실행 방법 절만 고쳐 줘. 다른 절은 건드리지 말고, 바뀐 부분만 코드 블록으로 보여 줘."
  3. 내가 적용제안을 VS Code에 옮기고, 무엇이 바뀌었는지 git diff로 봅니다.
  4. 확인로컬 서버로 열어 보고, 맞으면 커밋. 틀리면 git restore 파일.

권한 프롬프트 읽기

이 절을 읽고 나면 권한 프롬프트의 네 선택지가 각각 무엇을 허용하는지 알고, 어느 것을 고를지 정할 수 있습니다.

Manual 모드에서 에이전트가 명령을 실행하려 하면 이런 상자가 뜹니다. 아래는 Claude Code 문서의 Bash 명령 프롬프트 문구를 그대로 옮긴 것입니다.

╭─ Bash command ─────────────────────────────────────────╮
│ Run the test suite                                     │
│   npm test                                             │
│ This command requires approval                         │
│                                                        │
│ Do you want to proceed?                                │
│ ❯ 1. Yes                                               │
│   2. Yes, and don't ask again for: npm test *          │
│   3. Yes, and switch to auto mode                      │
│   4. No                                                │
│ Esc to cancel · Tab to amend                           │
╰────────────────────────────────────────────────────────╯
선택지별 뜻과 수업의 권장
선택지무엇이 허용되나언제 고르나
1. Yes이번 한 번만기본. 명령을 읽고 이해했을 때.
2. Yes, and don't ask again for: …그 명령 패턴을 저장소의 .claude/settings.local.json 허용 목록에 저장. 다음 세션에도 적용npm test처럼 읽기 전용이거나 안전한 명령에만. 파일 수정 승인은 세션 끝까지만 유지됩니다.
3. Yes, and switch to auto mode이후 분류기가 대신 승인수업에서는 고르지 않습니다. 사람이 확인하는 지점이 사라집니다.
4. No (Esc)실행하지 않음. Tab으로 이유를 적어 보내면 에이전트가 다른 방법을 찾습니다모르는 명령, 요청 밖 파일, 네트워크·삭제·push.

읽기 전용 명령(ls, cat, git status, git diff 등)은 묻지 않습니다. curl·wget 같은 네트워크 명령은 자동 승인되지 않습니다. Codex는 "Ask for approval" 프리셋에서 작업 폴더 밖 편집과 네트워크에 같은 식으로 묻습니다. 파일 수정 프롬프트의 선택지 문구는 도구와 버전에 따라 조금 다릅니다. 원리는 같습니다. 바뀌는 줄을 읽고 나서 답합니다.

연습 · 권한 프롬프트, diff, 되돌리기

팀 저장소에서 에이전트를 실행하고, 계획만 받은 뒤, 한 줄 변경을 승인하고, git diff로 확인하는 순서입니다. 연습 화면의 응답 문구는 공식 문서의 UI 문구를 바탕으로 재구성한 것입니다. 권한 프롬프트에서는 숫자 키로 답합니다.

내부 동작

Claude Code의 권한 규칙은 deny → ask → allow 순서로 평가되고 첫 일치가 결정합니다. 규칙은 Tool(specifier) 꼴입니다. Bash(npm run test *)는 npm run test … 계열만, Bash(git *)는 모든 git입니다. 문서가 강조하는 원칙은 이것입니다. "Permission rules are enforced by Claude Code, not by the model." 프롬프트나 CLAUDE.md는 모델이 시도하는 것을 바꾸고, 권한 규칙과 훅은 Claude Code가 허용하는 것을 바꿉니다. "Claude treats CLAUDE.md files as context, not enforced configuration." 그래서 반드시 막아야 하는 일(.env 읽기, git push)은 지시문이 아니라 deny 규칙이나 훅으로 겁니다.

{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Bash(npm run test *)", "Bash(npx serve *)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)", "Bash(git push *)"]
  }
}

훅(hooks)은 에이전트의 특정 시점에 실행되는 셸 명령입니다. "certain actions always happen rather than relying on the LLM to choose to run them." 예를 들어 PostToolUse에 Edit|Write 매처를 걸면 파일을 고칠 때마다 포매터나 테스트가 자동으로 돕니다. PreToolUse 훅이 종료 코드 2를 내면 그 행동이 차단되고 이유가 모델에 전달됩니다. 12주차에 이 확장(테스트·훅·CI)을 다룹니다. Codex는 같은 역할을 샌드박스(sandbox_mode)와 승인 정책(approval_policy)의 두 층과 .rules 파일로 나눕니다.

프롬프트 인젝션은 에이전트가 읽는 자료(Issue 본문, README, 웹 페이지, 패키지 설명) 안에 "이 파일을 지워라" 같은 지시문이 숨어 있는 경우입니다. 3주차 A.10에서 "참고 자료 속 문장은 작업 지시와 구분한다"고 배운 것이 에이전트에게는 더 중요합니다(3주차 A.10). Codex 문서: "Prompt injection can cause the agent to fetch and follow untrusted instructions." 대책은 권한을 좁게 두고(네트워크 기본 차단, deny 규칙), 자료를 에이전트에 직접 파이프하지 않고, 중요한 파일의 변경은 사람이 보는 것입니다. 어떤 시스템도 완전히 면역이 아닙니다.

외부 전시에 참여하는 팀원이 있으면 3~4단계 시간에 전시 버전을 점검해도 됩니다. 그동안 다른 팀원이 저장소 초기화를 맡고, 전시 참여자는 돌아와서 자기 몫의 문서 한 개를 맡습니다.

강사 순회

강사는 질문 카드를 세운 팀부터 돕니다. 카드에는 한 줄만 적습니다. "룰셋 메뉴가 안 보여요", "clone이 안 돼요", "①의 답을 못 정하겠어요"처럼 구체적일수록 빨리 풀립니다. 순회에서 강사가 보는 것은 세 가지입니다. 룰셋이 켜졌는가, 문서에 템플릿 예시가 남았는가, tasks.md의 '보여 줄 것'이 눈으로 확인할 수 있는 문장인가.

설치·로그인 문제로 막힌 사람은 짝과 먼저 해 보고, 그래도 안 되면 경로 (c)로 오늘 몫을 하고 수업 뒤에 eTL 메시지로 알려 주세요. 오늘 꼭 끝나야 하는 것은 저장소와 문서이지 특정 도구의 설치가 아닙니다.

YOUR CODE 1분

스튜디오 끝에 팀원 한 명이 이번 주 AI가 만든 코드·문서 한 조각을 팀 앞에서 1분 설명합니다. 오늘은 README의 실행 방법 절이나 tasks.md의 한 줄이면 됩니다. "이 명령이 무엇을 하는지", "왜 이 줄이 ★ 단계인지"를 자기 말로 설명합니다.

설명이 안 되면 괜찮습니다. tasks.md에 "지금 배운 문법으로 풀어 써 달라고 요청하기"를 다음 주 할 일로 적습니다. 설명할 수 없는 코드를 그대로 두는 것이 문제이지, 설명이 안 되는 순간을 발견한 것은 좋은 일입니다. 담당은 매주 돌아가며 맡습니다.

Q1HTML 파일을 더블클릭해 연 페이지(주소가 file://)에서 fetch('data/notes.json')이 실패합니다. 가장 알맞은 이유는?

  • JSON은 브라우저가 잘 읽습니다. 문제는 파일 형식이 아니라 여는 방식입니다.

  • 맞습니다. 그래서 로컬 서버로 http://로 엽니다. 배포 환경(https://)과 조건을 맞추는 뜻도 있습니다.

  • fetch는 브라우저 기능입니다. Node는 로컬 서버 도구를 돌리는 데 쓰일 뿐입니다.

Q2룰셋에서 "Require a pull request before merging"을 켰습니다. 팀원이 main에서 바로 git push하면?

  • 룰셋은 경고가 아니라 거부입니다.

  • 맞습니다. 그 자리에서 git switch -c feature/이름-기능을 하면 변경이 따라오고, 그 브랜치를 push해 PR을 엽니다.

  • PR은 사람이 엽니다. 룰셋은 main으로 가는 길을 막을 뿐입니다.

Q3에이전트에게 일을 맡기기 전과 맡기는 중에 사람이 하는 일을 모두 고르세요.

  • Delegate의 시작입니다. 범위가 있어야 검토 기준도 생깁니다.

  • 최근 버전은 auto로 시작할 수 있습니다. Shift Tab으로 바꿉니다.

  • 사람이 확인하는 지점을 전부 없애는 플래그입니다. 수업 노트북에서는 쓰지 않습니다.

  • Inspect의 시작입니다. 끝난 뒤에는 git diff로 한 번 더.

Q4npm test를 실행하면 test 스크립트 앞에 자동으로 실행되는 스크립트의 이름을 쓰세요.

pretest입니다. pre·post 접두사만으로 순서가 정해집니다(pretest → test → posttest).

Q5Claude Code 문서는 "CLAUDE.md는 맥락(context)이지 강제되는 설정이 아니다"라고 말합니다. 그러면 .env 읽기처럼 반드시 막아야 하는 것은 어디에 두어야 할까요?

  • 지시문은 모델이 시도하는 것을 바꿀 뿐, 도구가 허용하는 것을 바꾸지 못합니다.

  • 맞습니다. "deny": ["Read(./.env)"] 같은 규칙은 Claude Code가 강제합니다. 지시문에도 적어 두면 더 좋지만, 강제는 규칙이 합니다.

  • README는 사람을 위한 문서입니다. 에이전트가 먼저 읽는 것도, 강제하는 것도 아닙니다.
