강의 1 · 터미널

"어느 폴더에서, 무엇을 실행할지"를 글자로 적습니다

$ pwd              # 지금 어디에 있나
$ ls -a            # 숨김 파일까지 목록
$ cd team-app      # 들어가기 (te 까지 치고 Tab)
$ mkdir docs       # 폴더 만들기
$ code .           # 이 폴더를 VS Code로
$ node -v          # v22.12.0 이상이면 통과

Tab 자동 완성 · Ctrl C 멈추기 · ↑ 직전 명령. $는 치지 않습니다.

  • 왜 글자로? 같은 일을 정확히 되풀이, 남에게 그대로 전달, 에이전트가 같은 명령 실행.
  • 터미널 명령의 절반은 "지금 어디에 있나" 확인. 이번 주 할 일은 셋: 폴더 들어가기, 서버 띄우기, 에이전트 실행.
  • Windows는 PowerShell에서 같은 이름으로 동작(pwd, ls, cd, mkdir). 경로 구분자만 \ .
강의 1 · 자주 하는 실수

오류의 절반은 폴더 위치 문제입니다

$ npm run dev
npm ERR! enoent ENOENT: no such file or
directory, open '/Users/student/package.json'
$ pwd
/Users/student
$ cd team-app
$ npm run dev

명령이 실패하면 먼저 pwd로 어디에 있는지, ls로 기대한 파일이 보이는지 봅니다.

  • 실제로 홈 폴더에서 npm run dev를 쳐서 오류를 한 번 보여 주기. 그 다음 cd로 들어가 다시.
  • "No such file or directory", "package.json을 찾을 수 없음"이 모두 같은 종류.
강의 1 · npm

package.json의 scripts가 "실행 방법"입니다

{
  "name": "team-app",
  "private": true,
  "scripts": {
    "dev": "serve .",
    "test": "vitest run"
  }
}

npm run dev → serve . 실행. npx 이름은 설치 없이 한 번 실행합니다.

  • 긴 명령에 짧은 이름. 팀원과 에이전트가 같은 이름으로 같은 일을 한다.
  • 5주차 npx @tailwindcss/cli가 npx였다고 연결. 이번 주 설치할 패키지는 없음.
강의 1 · 예시

이름만으로 앞뒤 순서가 정해집니다

$ npm test

> pretest
> node check-node.js        # 1. 앞에 자동으로

> test
> vitest run                # 2. 본래 명령

> posttest
> echo 테스트 끝            # 3. 뒤에 자동으로

.gitignore에는 node_modules/ · dist/ · .env 세 줄. 지금 넣어 두면 나중에 실수로 올리지 않습니다.

  • pre·post 접두사 규칙. 확장판 실습 1(runOrder)은 자습으로 안내.
  • node_modules는 수천 개 파일, package.json만 있으면 다시 만들 수 있으니 저장소에 안 올림. 이미 올렸다면 git rm -r --cached node_modules.
강의 1 · 로컬 서버

더블클릭 대신 서버로 엽니다

file://

  1. 출처(origin)가 없다fetch가 막힙니다
  2. 모듈이 막힌다<script type="module">
  3. 배포와 조건이 다르다"배포하니 안 되네"

http://localhost:3000

  1. localhost이 컴퓨터
  2. 3000서버가 기다리는 문 번호(포트)
  3. 정적 서버요청마다 코드를 실행하지 않고 파일을 그대로
  • 2주차 08의 file:///C:/Users/… 주소를 떠올리게. 다음 주 fetch 코드가 전부 이 영향을 받는다.
  • 정적/동적 기준 "서버가 요청마다 코드를 실행하는가"(특강 때 들은 말) 회수.
  • 세 가지 도구(Live Server / npx serve / Vite)는 결과가 같다. 팀은 AGENTS.md에 하나를 적는다.
강의 1 · 라이브 데모

서버를 띄우고 Network 탭을 엽니다

$ npx serve .
Need to install the following packages:
serve@14.2.6
Ok to proceed? (y) y

   Serving!
   - Local:    http://localhost:3000

브라우저에서 주소를 열고, 개발자 도구 › Network 탭을 연 채 새로고침합니다.

  • 데모 순서: ① cd team-app ② npx serve . ③ 브라우저 localhost:3000 ④ F12 › Network ⑤ 새로고침 → index.html 200, style.css 200 ⑥ 주소창에 /없는파일.html → 빨간 404 ⑦ 터미널로 돌아와 Ctrl+C.
  • 서버가 쓰는 창에는 다른 명령 못 침 → 새 탭. 창을 그냥 닫으면 다음에 EADDRINUSE.
  • 실패 대비: 다운로드가 안 되면 Live Server(Go Live)로 같은 것, 또는 확장판 '연습 · 서버 띄우기' 화면.
  • 수업 직전 확인: serve 버전 표시(교안 14.2.6)는 달라져도 됨. 포트 바꾸기 -l 3001.
강의 1 · 요청과 응답

상태 코드는 첫 자리부터 읽습니다

2xx

성공 · 200 OK, 201 Created. 받은 데이터를 그립니다.

4xx

요청 쪽 문제 · 400, 401, 404. 주소·입력·키를 다시 봅니다.

5xx

서버 쪽 문제 · 500, 503. 내 코드 잘못이 아닐 수 있습니다.

3xx는 이동·그대로(304 캐시). 404를 받아도 fetch는 실패하지 않습니다 → 다음 주 res.ok.

  • "누구 잘못인가"를 첫 숫자가 말한다. 세 자리 다 외울 필요 없음.
  • Network 탭 한 줄 누르면 Headers › General에 URL·메서드·상태 코드. Type 열은 Content-Type에서.
강의 1 · 예시 (같이 실행)

연습용 서버에 세 요청을 보내 봅니다

  • 실행 → 네트워크 탭에서 200 · 404 · 500 세 줄. 500이 '알 수 없음'으로 찍히는 것을 보여 주고 TODO 한 줄 채우기.
  • 오프라인 스위치를 켜면 fetch가 TypeError로 실패 — "응답이 아예 없는 것"과 "404"의 차이.
  • 실패 대비: 확장판 실습 2(테스트 포함)를 화면에 띄우기.
강의 1 · 요청과 응답

헤더는 겉봉투, 본문은 내용물입니다

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 182
Cache-Control: max-age=0, must-revalidate
ETag: "a1b2c3"

[{"id":1,"topic":"HTTP","lines":["요청과 응답"]}]

Content-Type은 본문의 형식, Cache-Control은 얼마나 오래 재사용해도 되는지.

  • Network 탭 Headers 패널이 겉봉투. 빈 줄 아래가 본문.
  • JSON을 text/html로 주면 화면에 글자로 찍힌다 — Type 열이 왜 중요한지.
  • 심화(HTTP 캐시: ETag·304)는 확장판 03.9로 안내.
강의 1 · 자주 하는 실수

"고쳤는데 화면이 안 바뀌어요"

  1. Size 열에 "(memory cache)" 또는 304내 브라우저가 옛 사본을 쓰는 중
  2. 강력 새로고침Ctrl Shift R / ⌘ ⇧ R — 캐시를 무시하고 다시 받습니다
  3. 200인데 내용이 옛것Pages 배포 지연(최대 10분). 내 캐시가 아닙니다

Network 탭을 나중에 열면 목록이 비어 있습니다. 탭을 연 채 새로고침합니다.

  • 두 가지를 구분: 304/캐시 = 내 브라우저, 200인데 옛 내용 = 배포 지연.
  • 여기까지 강의 1. 12분 넘으면 헤더 슬라이드는 건너뛰어도 됨.
02

팀 저장소와 협업 규칙

룰셋 · 브랜치 · PR · 리뷰 · 충돌

  • 10분. 4주차 부록 D와 6주차 영상은 링크로. 오늘 새로운 것은 룰셋·충돌·PR 본문.
강의 2 · 왜 규칙인가

부딪혀도 안전하게 풀리도록, 설정으로 겁니다

  1. main은 PR로만직접 push는 거부. "Require a pull request before merging"
  2. 리뷰 1명자기 PR은 자기가 승인하지 않습니다. "Required approvals: 1"
  3. 지우기·강제 push 금지"Restrict deletions" · "Block force pushes"

공개(Public) 저장소여야 Pages와 룰셋을 무료로 씁니다. 약속은 깨져도 설정은 지켜집니다.

  • 다섯 명 + 에이전트가 커밋하면 약속만으로는 안 된다. 사람이 깜빡해도, 에이전트가 시도해도 설정은 지켜진다.
  • OT의 GitHub 흐름 그대로: Issue → Branch → AI 작업 → Diff·Test → PR → Review·Merge.
  • 확인 필요: 저장소 소유 방식(강사 Organization vs 팀 대표 계정 + Collaborator). 어느 쪽이든 Public.
강의 2 · 예시

main에 직접 push하면 이렇게 거부됩니다

$ git push origin main
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Changes must be made through a pull request.
 ! [remote rejected] main -> main (push declined due to repository rule violations)

거부는 실패가 아니라 규칙이 작동한 것입니다. 그 자리에서 git switch -c feature/이름-기능 → push → PR.

  • 스튜디오에서 일부러 한 번 겪어 보라고. 변경은 새 브랜치로 따라온다.
  • "Bypass list"에는 아무도 넣지 않기. 강사가 저장소를 볼 때 룰셋 Active, 승인 1 확인.

강의 2 · 브랜치와 PR

한 번의 작업은 이 여덟 줄입니다

$ git switch main && git pull            # 남의 변경을 먼저 받습니다
$ git switch -c feature/팀원1-readme     # 브랜치를 만들고 옮깁니다
# … 파일을 고칩니다 …
$ git status                              # 무엇이 바뀌었나
$ git diff                                # 어떤 줄이 바뀌었나
$ git add README.md
$ git commit -m "docs: README에 실행 방법 추가"
$ git push -u origin feature/팀원1-readme # 처음 한 번만 -u

브랜치 이름은 feature/이름-기능. GitHub 화면의 "Compare & pull request"로 PR을 엽니다.

  • git pull을 먼저 하는 이유: 오래된 main에서 시작하면 나중에 충돌이 커진다.
  • git diff는 에이전트가 고친 것도 여기서 읽는다 — 강의 3과 연결.
  • 병합 뒤: git switch main → git pull → git branch -d 브랜치.

강의 2 · 충돌

충돌은 같은 줄을 다르게 고쳤을 때만 납니다

# 메모 분류
<<<<<<< HEAD
실행: npx serve .
=======
실행: npx serve src
>>>>>>> origin/main
빌드 없음

HEAD 쪽이 내 것, 아래가 상대 것. 하나로 정리하고 표시 줄 세 개를 반드시 지웁니다.

  • 다른 줄을 고쳤으면 Git이 알아서 합친다. 충돌은 Git이 "못 고르겠다"고 멈춘 것, 실패가 아님.
  • 셋 중 하나: 내 것, 상대 것, 둘을 합친 새 문장.
강의 2 · 예시

충돌 풀기 네 단계

  1. git pull origin mainCONFLICT … 정상입니다
  2. 파일 정리VS Code의 Accept Current / Incoming / Both
  3. git add README.md정리한 파일을 올립니다
  4. git commit병합 커밋 한 줄

충돌을 풀었다고 코드가 맞는 것은 아닙니다. 로컬 서버로 열어 README의 명령이 실제로 맞는지 보고 push합니다.

  • 확장판 '연습 · 충돌 해결' 화면을 띄워 한 번 같이 클릭해도 됨(2분).
  • 표시 줄을 남긴 채 커밋하면 페이지에 <<<<<<< HEAD가 글자로 보인다 — 검색해서 정리.
  • 휴식 10분은 여기서.

강의 3 · 라이브 데모

첫 요청은 "읽고 제안만"

  • 데모 순서: ① git status 깨끗한지 ② 프로젝트 폴더에서 에이전트 실행(처음 폴더면 '신뢰' 대화상자) ③ Shift+Tab으로 manual ④ 위 요청 ⑤ 제안 읽기 — ⑧ 범위 대조 ⑥ "1번 줄만 tasks.md에 추가, 다른 줄은 건드리지 마" ⑦ diff 읽고 1(Yes) ⑧ 새 탭에서 git diff docs/tasks.md ⑨ /usage 한 번.
  • 되돌리기 시연: git restore docs/tasks.md 한 줄. 에이전트 안에서는 /rewind.
  • 실패 대비(로그인·네트워크): 확장판 '연습 · 권한 프롬프트, diff, 되돌리기' 화면을 띄워 숫자 키로 같이 진행. ChatGPT Edu 웹이면 '연습 · ChatGPT Edu에서 같은 요청' 화면.
  • 확인 필요: 데모용 폴더에 docs/requirements.md(메모 분류 예시)와 AGENTS.md가 들어 있는지.
