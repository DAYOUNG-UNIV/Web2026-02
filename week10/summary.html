팀 저장소와 작업 환경

지난주에 정한 알파 버전의 범위를 담을 그릇을 만듭니다. 터미널에서 프로젝트를 열고, 로컬 서버를 띄워 요청과 응답을 읽고, 팀 저장소에 보호 규칙을 걸고, AI 코딩 에이전트를 연결한 뒤, 팀 시트를 하네스 문서 여섯 개로 옮겨 적습니다.

  • 읽는 시간 약 10분
  • 자세한 설명과 실습 확장판 · 수업용 발표
  • AI 등급 AI REQUIRED (세 경로 중 하나)

학습 목표

  1. 터미널에서 프로젝트 폴더를 다루고 로컬 서버를 띄운 뒤, Network 탭에서 요청과 응답(메서드·상태 코드·헤더)을 읽을 수 있다.
  2. 팀 저장소를 만들고 룰셋으로 main을 보호하며, 브랜치와 PR로 협업하고 같은 줄 충돌을 해결할 수 있다.
  3. AI 코딩 에이전트를 프로젝트에 연결하고, 권한을 수동으로 둔 채 변경을 확인하고 되돌릴 수 있다.
  4. 하네스 문서(requirements·tasks·checklist·design·architecture + AGENTS.md 또는 CLAUDE.md)를 팀 시트에서 옮겨 쓸 수 있다.

핵심 개념

터미널은 "어느 폴더에서, 무엇을 실행할지" 적는 창입니다

명령 다섯 개와 키 두 개(Tab 자동 완성, Ctrl C 멈추기)면 이 수업의 터미널 작업은 됩니다. 명령 앞의 $는 "여기에 입력한다"는 표시이고 직접 치지 않습니다. Node는 v22.12.0 이상이면 통과입니다.

$ pwd              # 지금 어디에 있나
$ ls -a            # 숨김 파일까지 목록
$ cd team-app      # 들어가기 (te 까지 치고 Tab)
$ mkdir docs       # 폴더 만들기
$ code .           # 이 폴더를 VS Code로
$ node -v          # v22.12.0 이상이면 통과

"No such file or directory", "package.json을 찾을 수 없음" 같은 오류의 절반은 폴더 위치 문제입니다. 명령이 실패하면 먼저 pwd와 ls로 지금 어디에 있는지 확인합니다.

확장판에서 더 보기

package.json의 scripts가 "실행 방법"입니다

npm run 이름은 scripts 칸에서 이름을 찾아 오른쪽 명령을 실행합니다. pretest·posttest처럼 이름만으로 앞뒤 순서가 정해집니다. npx 이름은 설치 없이 한 번 실행합니다. node_modules/는 .gitignore에 적어 저장소에 올리지 않습니다.

{
  "name": "team-app",
  "private": true,
  "scripts": {
    "dev": "serve .",
    "test": "vitest run"
  }
}

프로젝트 밖에서 npm run dev를 치면 ENOENT: no such file … package.json이 납니다. cd로 들어간 뒤 다시 합니다. node_modules를 이미 커밋했다면 git rm -r --cached node_modules로 추적을 끊습니다.

확장판에서 더 보기

file:// 대신 로컬 서버로 엽니다

더블클릭으로 연 페이지(file://)에는 출처(origin)가 없어 fetch와 <script type="module">이 막힙니다. 로컬 서버는 내 컴퓨터 안의 작은 웹 서버로, 폴더의 파일을 http://localhost:3000으로 돌려줍니다. 배포(https://)와 같은 조건입니다.

$ npx serve .
   Serving!
   - Local:    http://localhost:3000

서버를 켠 터미널 창을 그냥 닫으면 다음에 EADDRINUSE … :3000이 납니다. 멈출 때는 Ctrl C. 이미 났다면 npx serve -l 3001로 다른 포트를 씁니다.

확장판에서 더 보기

Network 탭에서 상태 코드는 첫 자리부터 읽습니다

Network 탭은 페이지가 보낸 모든 요청과 받은 응답의 기록입니다. 상태 코드의 첫 숫자가 "누구 잘못인가"를 말합니다. 2xx 성공, 3xx 이동·그대로(304), 4xx 요청 쪽 문제(404), 5xx 서버 쪽 문제. 응답 헤더 Content-Type은 본문의 형식, Cache-Control은 재사용 기간입니다. 404를 받아도 fetch는 실패하지 않으므로 res.ok를 직접 봅니다. 아래에서 500번대 한 줄을 채워 테스트를 통과시켜 보세요.

Network 탭을 나중에 열면 목록이 비어 있습니다. 탭을 연 채 새로고침합니다. 고쳤는데 화면이 안 바뀌면 Size 열의 "(memory cache)"나 304를 보고 강력 새로고침(Ctrl Shift R)을 합니다.

룰셋으로 main을 보호합니다

다섯 명과 에이전트가 한 저장소에 커밋하면 약속만으로는 부족합니다. 저장소 Settings › Rules › Rulesets에서 main에 규칙 셋을 겁니다. PR 필수(승인 1명), 삭제 금지, 강제 push 금지. 공개(Public) 저장소여야 Pages와 룰셋을 무료로 쓸 수 있습니다. 직접 push하면 아래처럼 거부됩니다.

$ git push origin main
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Changes must be made through a pull request.
 ! [remote rejected] main -> main (push declined due to repository rule violations)

main에서 바로 고치고 push해 거부당했다면 그 자리에서 git switch -c feature/이름-기능을 합니다. 변경이 새 브랜치로 따라오고, 그 브랜치를 push해 PR을 엽니다. 거부는 실패가 아니라 규칙이 작동한 것입니다.

확장판에서 더 보기

브랜치에서 고치고 PR로 제안합니다

브랜치 이름은 feature/이름-기능으로 통일합니다. PR 본문은 세 칸(무엇을·왜·어떻게 확인했나)과 검토 6단어(동작·범위·복잡성·접근성·보안·개인정보)입니다. 리뷰어는 병합을 막는 의견(Request changes)과 제안(Comment)을 구분하고, 자기 PR은 자기가 승인하지 않습니다.

$ git switch main && git pull            # 남의 변경을 먼저 받습니다
$ git switch -c feature/팀원1-readme
# … 파일을 고칩니다 …
$ git diff                                # 어떤 줄이 바뀌었나
$ git add README.md
$ git commit -m "docs: README에 실행 방법 추가"
$ git push -u origin feature/팀원1-readme

오래된 main에서 브랜치를 시작하면 PR에 "This branch has conflicts"가 뜹니다. 브랜치를 만들기 전에 git pull로 main을 최신으로 둡니다.

충돌은 같은 줄을 다르게 고쳤을 때만 납니다

다른 줄을 고쳤으면 Git이 알아서 합칩니다. 충돌이 나면 Git은 멈추고 파일 안에 두 버전을 나란히 적습니다. HEAD 쪽이 내 것, 아래가 상대 것입니다. 내 것·상대 것·둘을 합친 새 문장 중 하나로 정리하고 표시 줄 세 개를 지운 뒤 git add, git commit합니다.

# 메모 분류
<<<<<<< HEAD
실행: npx serve .
=======
실행: npx serve src
>>>>>>> origin/main
빌드 없음

표시 줄을 남긴 채 커밋하면 페이지에 <<<<<<< HEAD가 글자로 보입니다. 파일에서 <<<<<<<를 검색해 모두 정리하고 다시 커밋합니다. 충돌을 풀었다고 코드가 맞는 것은 아니니 로컬 서버로 한 번 열어 봅니다.

자가 점검 퀴즈

Q1터미널에서 npm run dev를 쳤더니 ENOENT: no such file … package.json이 나왔습니다. 가장 먼저 할 일은?

  • Node는 이미 명령을 실행했습니다. 파일을 못 찾은 것이 문제입니다.

  • 맞습니다. 프로젝트 밖에서 실행한 것입니다. cd로 package.json이 있는 폴더에 들어간 뒤 다시 합니다.

  • 파일은 이미 프로젝트 폴더에 있습니다. 위치를 먼저 봅니다.

Q2로컬 서버를 켜고 Network 탭에 404가 빨갛게 보입니다. 무슨 뜻인가요?

  • 서버가 죽었다면 응답 자체가 없습니다. 404는 서버가 보낸 응답입니다.

  • 맞습니다. 4xx는 요청 쪽 문제입니다. 주소나 파일 이름을 다시 봅니다. fetch는 404에도 실패하지 않으므로 res.ok를 직접 검사합니다.

  • 문법 오류는 Console 탭에 나옵니다. Network 탭의 숫자는 요청·응답의 결과입니다.

Q3에이전트에게 일을 맡기기 전과 맡기는 중에 사람이 하는 일을 모두 고르세요.

  • Delegate의 시작입니다. 범위가 있어야 검토 기준도 생깁니다.
