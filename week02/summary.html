웹페이지를 만든다는 것

브라우저는 주소로 서버에 요청하고, 받은 HTML을 해석해 화면에 그립니다. HTML은 글자를 꾸미는 언어가 아니라 의미를 표현하는 언어입니다. 여기에 AI에 제공할 정보의 범위를 스스로 정하는 연습까지가 2주차입니다.

  • 읽는 시간 약 10분
  • 자세한 설명과 실습 확장판
  • 과제 과제 1 · HTML로 나를 소개하기

학습 목표

  1. 인터넷과 웹을 구분하고, 주소 입력부터 화면 표시까지(주소 조회 → 요청 → 응답 → 렌더링)를 설명할 수 있다.
  2. 제목·문단·목록·링크를 의미에 맞는 HTML 요소로 쓰고, 그 요소를 고른 이유를 말할 수 있다.
  3. lang·제목 계층·alt·시맨틱 태그가 왜 접근성인지 설명하고 키보드로 점검할 수 있다.
  4. 저장·커밋·전송·배포를 구분하고, VS Code와 Live Server로 고친 결과를 확인할 수 있다.
  5. AI에 제공할 정보의 범위를 스스로 정하고, 받은 결과를 검토해 기록할 수 있다.

오늘의 지도

2주차는 개인 구간(2~7주)의 첫 주입니다. HTML에서 시작해 3주차 CSS, 4주차 레이아웃, 5주차 JavaScript로 이어집니다.

  1. 주소를 설명한다인터넷·웹·요청과 응답
  2. 의미를 구조로 쓴다제목·문단·목록·링크
  3. 고치고 확인한다예측 → 수정 → 관찰
  4. 정보의 범위를 정한다선택한 내용만 eTL 제출

핵심 개념

인터넷과 웹은 같은 것이 아닙니다

인터넷은 컴퓨터와 컴퓨터를 연결하는 네트워크이고, 웹은 그 위에서 돌아가는 여러 서비스(웹·이메일·온라인 게임) 중 하나입니다. eTL 공지를 열 때 내 브라우저는 요청하는 쪽(클라이언트)이고, 웹 서버는 요청을 받아 자료로 응답하는 쪽이며, DNS는 이름에 대응하는 IP 주소를 조회할 뿐 본문을 보내지 않습니다.

1969년은 인터넷의 전신인 ARPANET의 출범 연도이고, 웹은 1989년에 제안됐습니다. 주소창이 검색도 지원하므로 브라우저와 검색 엔진도 구별합니다.

확장판에서 더 보기

한 페이지가 열리기까지

주소 조회(DNS) → 페이지 요청(HTTP) → 응답 → 화면 표시 순서입니다. 받은 HTML과 CSS를 해석해 화면으로 만드는 과정이 렌더링입니다.

① 브라우저 → DNS     info.cern.ch 어디 있어?
② DNS → 브라우저     188.184.100.182
③ 브라우저 → 웹 서버  GET /hypertext/WWW/TheProject.html
④ 웹 서버 → 브라우저  200 OK + HTML 파일
⑤ 브라우저            HTML → DOM, CSS → CSSOM → 렌더 트리 → 레이아웃 → 페인트

도중에 <script>를 만나면 브라우저는 HTML 파싱을 멈추고 스크립트를 먼저 실행합니다. 스크립트를 아무 데나 넣으면 페이지가 늦게 뜹니다.

URL · HTTP · HTML, 그리고 주소의 조각

셋은 따로 있는 기술이 아니라 한 동작의 세 부분입니다. 주소로 가리키고(URL), 정해진 방식으로 요청해서 받아오고(HTTP), 받아온 것이 HTML 문서입니다. https의 s는 secure로, TLS로 통신을 보호합니다.

접속 방식  호스트(이름)      경로         쿼리        프래그먼트
HTTPS     어디로 접속하나    어떤 자원인가  덧붙이는 값   문서 안의 위치

#syllabus 같은 프래그먼트는 서버로 전송되지 않습니다. 브라우저만 씁니다. 로그인 정보를 입력할 때는 HTTPS 연결인지 먼저 확인합니다.

웹페이지를 이루는 세 가지 언어

HTML은 무엇이 있는가(구조·의미), CSS는 어떻게 보이는가(표현), JavaScript는 무엇을 하는가(동작)를 맡습니다. 아래 예시에서 JavaScript는 getElementById로 요소를 찾고, onclick으로 클릭 처리를 지정하고, textContent로 내용을 바꿉니다. 이번 주는 HTML만 다루며, 과제에서 CSS는 필수가 아니고 평가하지 않습니다.

<p id="msg">클릭 횟수: 0</p>
<button id="btn">클릭 횟수 확인</button>
<script>
  const btn = document.getElementById("btn");
  const msg = document.getElementById("msg");
  let count = 0;
  btn.onclick = function () { count = count + 1; msg.textContent = count + "번 눌렀습니다."; };
</script>

글자 크기나 색을 바꾸려고 HTML 태그를 고르지 않습니다. 모양은 CSS의 일이고, HTML은 의미를 정합니다.

요소·속성, 그리고 문서의 뼈대

여는 태그 + 내용 + 닫는 태그를 통틀어 요소라고 하고, 속성은 여는 태그 안에만 씁니다. 요소는 중첩할 수 있지만 교차해서는 안 됩니다. VS Code에서 !를 입력하고 Tab을 누르면 아래 뼈대가 생깁니다.

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>나를 소개합니다</title>
</head>
<body>
  <p>학교: <a href="https://www.snu.ac.kr">서울대</a></p>
</body>
</html>

Emmet이 만든 lang="en"은 ko로 고칩니다. 워드·카카오톡에서 복사한 코드는 따옴표가 둥근 “ ”로 바뀌어 동작하지 않습니다. 주석은 숨김이 아니므로 비밀번호·API 키를 넣지 않습니다.

제목은 글씨 크기가 아니라 계층입니다

h1은 문서의 최상위 제목이고, 크게 보이는 것은 브라우저 기본 스타일의 결과일 뿐입니다. 이번 과제에서는 h1 하나, 하위 제목은 h2·h3 순서로 둡니다. 중요성에는 strong, 문장의 강세에는 em을 쓰고, 굵기만 바꾸려면 CSS를 씁니다. 아래 '망가진 코드'를 고쳐 테스트를 통과시켜 보세요.

글씨를 작게 하려고 h1을 h3으로 바꾸면 제목 단계가 달라집니다. 문단 사이를 띄우려고 <br><br>을 쓰지 않습니다. 여백은 CSS의 일입니다.

이미지와 alt

alt는 이미지를 볼 수 없을 때 대신 전달되는 글로 된 설명입니다. 정보를 전달하면 그 정보를, 클릭 기능이면 목적을, 순수 장식이면 alt=""를 씁니다. width·height를 미리 적으면 화면이 덜컹거리지 않습니다.

<img src="images/photo.jpg" alt="창가에 앉은 고양이" width="600" height="400" loading="lazy">
<img src="images/line.png" alt="">  <!-- 순수 장식: 스크린 리더가 건너뜁니다 -->

alt를 생략하는 것과 빈 값으로 지정하는 것은 다릅니다. 생략하면 스크린 리더가 파일 이름 등을 읽을 수 있습니다. 휴대폰 사진 원본은 가로 1200px 정도로 줄인 뒤 씁니다.

시맨틱 태그 — 모두가 읽을 수 있는 페이지

header·nav·main·section·article·aside·footer는 내용의 역할을 코드에 적고, 스크린 리더는 이런 랜드마크로 본문에 바로 이동합니다. 딱 맞는 의미의 태그가 있으면 그것을 쓰고, 없을 때만 div를 씁니다. lang="ko"(한국어 발음으로 읽기)·제목 계층(제목만 훑어 건너뛰기)·alt·랜드마크·목적이 드러나는 링크 이름은 모두 같은 이야기, 접근성이며 가장 확실한 점검은 마우스 없이 Tab으로 써 보는 것입니다.

main은 페이지에 하나뿐이고, section과 article의 차이는 "떼어내도 말이 되는가"입니다. "여기를 클릭" 같은 링크 이름, 색으로만 알리는 오류, 클릭 처리만 붙인 div는 보조 기술에 전달되지 않습니다.

Markdown과 README, 그리고 VS Code·Live Server

Markdown은 일반 텍스트 안에 #과 - 같은 기호로 제목과 목록을 표시하는 작성 방식입니다. 웹페이지의 구조는 HTML로, 프로젝트 설명과 활동 기록은 Markdown(README.md)으로 쓰며, README.md·AGENTS.md·CLAUDE.md는 AI 코딩 도구가 읽는 설명서로도 쓰입니다. 실습은 프로젝트 폴더를 먼저 만들어 VS Code로 열고, Live Server(Go Live)의 http://127.0.0.1:5500 같은 로컬 주소에서 확인합니다(127.0.0.1은 "내 컴퓨터 자신", 5500은 포트 번호).

저장·커밋·전송·배포는 서로 다른 행동입니다

Git은 내 컴퓨터에 설치해 파일이 언제 어떻게 바뀌었는지 기록하는 프로그램이고, GitHub은 그 기록을 올려두고 나누는 웹 서비스입니다. 저장(Ctrl S)은 내 파일만 갱신하고, 커밋은 로컬 이력에 기록하고, push는 원격 저장소로 보내고, 웹 공개는 Pages 같은 배포 설정이 합니다.

$ git add index.html
$ git commit -m "관심 분야 섹션 추가"
$ git push

커밋했다고 인터넷에 올라가지는 않습니다. 파일 이름에 "최종2", "진짜최종"을 붙이는 대신 커밋 메시지에 무엇을 왜 바꿨는지 한 줄 적습니다. 이번 과제 파일은 GitHub에 올리지 않고 eTL에만 제출했습니다.

AI와 함께 · 2주차 요약

이번 주 등급은 AI ALLOWED입니다. 코드 초안을 AI에 맡길 수 있으며, 핵심 구조와 선택 이유, 확인 방법은 직접 설명합니다.

  • 검토 절차 — 읽게 하기("현재 index.html의 구조를 설명해줘") → 배우기("h1, h2, p, ul, li가 각각 어떤 역할인지") → 검토받기(아래 요청). AI 초안으로 시작했어도 같은 질문으로 구조를 확인하고, 적어도 한 부분을 의도에 맞게 직접 고친 뒤 실행 결과를 확인합니다.
  • 정보의 범위 — 내가 보낸 말이 남는 곳은 네 가지(화면의 대화 기록 / 메모리·대화 참조 / 모델 개선 활용 / 서버 보관)이며 따로 확인합니다. 학습에 쓰지 않는다는 말은 아무 기록도 남지 않는다는 말이 아닙니다. 줄이는 방법: 구조와 내용 분리, [이름] 같은 플레이스홀더, 범주화, 가명, 로컬에서 먼저 쓰기. 비밀번호·API 키·개인정보가 든 파일을 열어 둔 채 작업하지 않습니다.
  • 기록 — 과제에는 AI 사용 기록을 함께 냅니다. 사용한 도구, 요청 내용, 채택·거절한 제안, 직접 수정한 부분(2주차에는 REFLECTION.md, 이후 과제에서는 AI USE NOTE). 도구는 서울대 ChatGPT Edu, Codex IDE 확장(수업 시연 환경), Claude Code(선택), 브라우저 챗 어느 것이든 되며, 제품 선택은 평가 기준이 아닙니다.
