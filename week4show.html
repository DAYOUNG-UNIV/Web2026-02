CSS의 display를 바꾸어도 태그의 의미와 중첩 규칙은 그대로입니다. 어떤 요소를 안에 넣을 수 있는지는 HTML의 규칙을 따릅니다.
<div class="group">
  <p>첫 번째 문단</p>
  <div>별도의 내용 묶음</div>

flex의 세 속성 · grow, shrink, basis

absolute는 어떤 상자를 기준으로 놓일까요?

1안쪽부터 확인

2기준 상자

항상 바로 위 부모가 기준인 것은 아닙니다. transform 등의 속성도 absolute·fixed의 기준 상자를 만들 수 있습니다. 해당 조상이 없으면 absolute는 초기 containing block, fixed는 보통 뷰포트를 기준으로 합니다.

스크롤할 때 fixed와 sticky는 어떻게 다를까요?
① → ② → ③을 차례로 누릅니다. sticky는 처음에는 문서와 함께 움직이다가 위쪽 12px 경계에 붙고, 부모 영역이 끝나면 함께 사라집니다. fixed는 처음부터 같은 위치에 남습니다.

  position: static;
  top: 12px;
}
sticky
.bar {
  position: sticky;
  top: 12px;
}
fixed
.bar {
  position: fixed;
  top: 12px;
}
각 결과 창이 뷰포트 역할을 합니다. 화면 안을 스크롤하거나 단계 버튼을 누르면 세 화면의 스크롤 위치가 함께 바뀝니다.

06.06 · 반응형과 사용성
이미지가 부모 영역을 넘지 않게 합니다
CSS로 표시 크기를 조절하는 방법과, 화면 조건에 맞는 이미지 파일을 선택하는 방법을 살펴봅니다.
srcset과 sizes · 선택
srcset은 후보 파일과 너비 또는 배율을, sizes는 예상 표시 폭을 제공합니다. 브라우저가 환경을 고려해 후보를 선택합니다. object-fit은 내려받을 파일을 고르는 기능이 아니라 정해진 상자 안의 표시 방식을 정합니다.
<img src="menu-480.jpg"
     srcset="menu-480.jpg 480w, menu-960.jpg 960w"
     sizes="(max-width: 600px) 100vw, 480px"
     alt="카페 메뉴 안내">
같은 이미지를 480px와 960px 너비의 파일로 준비해 연결합니다. 480w·960w는 각 파일의 픽셀 너비를 나타냅니다.
width: 100%의 기준은 보통 이미지가 놓인 부모의 내용 영역입니다. vw는 뷰포트 폭을 기준으로 합니다. 부모 폭과 화면 폭이 항상 같은 것은 아닙니다.

사진첩을 살펴보며 어떤 장면에 자주 눈길이 갔는지, 그 사진이 지금 자신에게 어떤 의미인지 생각해 봅니다. 이 과정에서 발견한 관심사나 질문을 전시 주제로 정합니다.
01
사진에서 출발하기
반복해서 찍은 대상이나 색, 오래 남겨 둔 장면을 찾아봅니다. 사진을 골랐던 이유도 함께 떠올립니다.
02
나의 시선 찾기
사진 사이의 공통점은 무엇인가요? 당시의 나와 지금의 나는 같은 장면을 어떻게 다르게 보나요?
03
전시로 구성하기
발견한 관심사나 질문을 제목으로 정하고, 사진의 순서와 캡션으로 관람객에게 전달합니다.
주제는 일상의 기록부터 기억·시간·죽음처럼 추상적인 생각까지 자유롭습니다. “사진첩에 반복되는 색”, “내가 없는 하루”, “미래의 내가 돌아보는 오늘” 등은 예시입니다.
08.03 · 개인 과제 · 온라인 사진 전시회
사진 공유가 불편하다면 AI 이미지로 대체할 수 있습니다
본인이 촬영한 사진을 사용하는 것이 기본입니다. 사진 공유에 불편함을 느끼는 학생은 일부 또는 전체를 본인이 AI로 생성한 이미지로 대체할 수 있습니다. 이 경우에도 주제와 작품 구성은 본인의 관찰과 생각에서 출발합니다.
01
작품에 표시
대체한 작품의 캡션에 “AI 생성 이미지”라고 적습니다. 직접 촬영한 사진과 함께 쓰더라도 각 작품을 구별할 수 있어야 합니다.
02
생성한 이유 설명
README에 해당 작품과 생성 도구를 적고, 왜 그 장면이 전시 주제에 필요한지 설명합니다. 개인적인 불편함의 사유는 적지 않아도 됩니다.
작성 예시 · 실제 작품 정보에 맞게 바꿉니다.
캡션: “남겨진 자리 — AI 생성 이미지”
README: “작품 2는 [사용한 도구]로 생성했습니다. 사람이 떠난 뒤 남은 흔적을 표현하려고, 빈 의자와 식어 가는 찻잔이 있는 장면을 만들었습니다.”

PR을 병합하면 GitHub의 기준 브랜치에 변경이 반영됩니다. 각자의 컴퓨터에서도 기준 브랜치로 이동해 변경을 가져옵니다.
1병합 전
최신 diff·실행 결과·권한·저장소 규칙 확인
2원격 병합
선택한 방식으로 main에 반영
3로컬 갱신
기본 브랜치로 전환 후 가져와 실행 확인
기본 브랜치가 main이고 로컬 변경을 정리한 예
git status
git switch main
git pull --ff-only
다른 로컬 변경이 있거나 이력이 갈라졌다면 먼저 상태를 확인합니다. 현재 작업을 잃지 않도록 중단 이유를 읽습니다.
병합한 페이지를 열고 입력·제출 동작을 검사합니다. 병합이 끝났어도 코드의 동작에 오류가 있을 수 있습니다.

공유한 변경은 되돌림도 기록합니다
병합 뒤 문제가 확인되면 영향과 되돌릴 범위를 합의하고, 되돌리는 변경을 새 기록으로 남길 수 있습니다.
1문제 확인
어떤 입력에서 언제부터 잘못되는지 재현
2되돌림 제안
해당 변경을 되돌리는 PR 또는 커밋 작성
3검토·반영
정상 동작과 다른 개선의 유지 여부 확인
공통 기록 A → 개선 M → 되돌림 R
                      └ R도 새로운 기록입니다.
GitHub의 Revert 기능은 병합한 PR을 되돌리는 새 PR을 만들 수 있습니다. 권한·병합 방식·충돌에 따라 수동 처리가 필요할 수 있습니다. 되돌린 뒤에도 파일과 동작을 다시 확인합니다.

E.04 · Git·GitHub 기초 참고 보충·참고 기초 참고
push와 pull의 방향을 구분합니다
로컬 커밋을 보낼 때와 원격 변경을 가져올 때 사용하는 동작입니다.
필요할 때 펼쳐보기 · Git 기초
1로컬 → 원격
push: 로컬의 커밋을 원격에 전달
2원격 → 로컬
fetch: 원격 이력을 가져옴
3가져오기 + 통합
pull: fetch 후 설정·옵션에 따라 merge 또는 rebase 등으로 통합
git status
git pull
git push
위 명령은 원격·브랜치 연결이 준비된 경우의 예입니다. 로컬 변경을 먼저 확인합니다. pull은 언제나 단순 덮어쓰기가 아니며 충돌이나 전략 선택이 필요할 수 있습니다.
