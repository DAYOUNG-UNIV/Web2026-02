AI와 함께 일하는 법: 6단계, 도구, 금지선, AI USE NOTE

이 수업에서 AI 사용은 예외가 아니라 기본입니다. 이 페이지는 OT에서 약속한 AI 정책을 실제 과제에 붙이는 출발점입니다. 여섯 단계를 한 바퀴 돌아 보고, 어떤 도구를 써도 같은 원리라는 것을 확인한 뒤, 하지 말아야 할 네 가지와 기록하는 법을 익힙니다.

진행 상황을 표시하며 따라가세요. 표시는 이 브라우저에만 저장됩니다.

6단계 워크플로와 주차 대응

이 절을 읽고 나면 "AI에게 맡긴다"가 한 번의 요청이 아니라 여섯 단계라는 것을 알고, 지금 주차가 어느 단계인지 말할 수 있습니다.

OT에서 약속한 AI-Native Workflow는 여섯 단계입니다. 요청 한 줄로 끝나는 일은 거의 없습니다. 무엇을 만들지 정하고, 맡기고, 읽고, 돌려 보고, 고치고, 저장소에 넣습니다. 한 과제 안에서 이 바퀴를 한 번 돌고, 학기 후반부에서는 주차마다 한 단계에 무게를 둡니다.

Define · 문제 정의
무엇을, 어떤 모양으로, 하지 말 것은 무엇인지 적습니다. 예: "메모 배열과 태그를 받아 그 태그가 붙은 메모만 돌려주는 함수 하나. 라이브러리 없이."
Delegate · AI 위임
정의한 범위만큼 맡깁니다. 범위가 넓으면 결과를 읽을 수 없습니다. 한 번에 한 파일, 한 기능.
Inspect · 검토
받은 코드를 한 줄씩 읽습니다. 모르는 줄이 있으면 그 줄부터 묻습니다. 요청 밖의 파일을 건드리지 않았는지 봅니다.
Test · 테스트
직접 실행합니다. 브라우저에서 눌러 보고, Network 탭을 열고, 테스트를 돌립니다. AI의 "됩니다"는 아직 주장입니다.
Revise · 수정
틀린 곳을 고치거나, 범위를 좁혀 다시 맡깁니다. 같은 지적이 두 번 나오면 지시 파일(AGENTS.md·CLAUDE.md)에 규칙으로 적습니다.
Integrate · 통합
커밋과 PR은 사람이 검토한 뒤에 합니다. 무엇을 맡겼고 무엇을 확인했는지 AI USE NOTE에 남깁니다.

하네스: 에이전트는 무엇을 먼저 읽고 어떻게 반복하나

내부 동작
코딩 에이전트는 요청을 받으면 '맥락 모으기 → 행동 → 결과 확인'을 반복합니다(공식 문서의 agentic loop: gather context → take action → verify results). 모델을 감싸고 도구와 맥락을 관리하는 이 바깥 층을 Claude Code 문서는 "agentic harness"라고 부릅니다. OT의 하네스 엔지니어링(Intent · Context · Tasks · Guardrails · Verify · Feedback)과 같은 말입니다. Codex 문서는 "Codex reads AGENTS.md files before doing any work"라고 적고, Claude Code는 CLAUDE.md를 읽으며 저장소의 AGENTS.md도 읽습니다.
명세·문서
Claude Code · How Claude Code works · Codex · AGENTS.md · OT · Harness Engineering
트레이드오프
지시 파일은 '맥락'이지 '강제'가 아닙니다. Claude Code 문서는 "Claude treats CLAUDE.md files as context, not enforced configuration"이라고 씁니다. 꼭 막아야 하는 것(비밀 파일 읽기, git push)은 권한 규칙과 훅으로 막습니다. 반대로 지시 파일이 길어지면(권장 200줄 이하) 중요한 규칙이 묻힙니다.
5분 실험
04의 '권한 규칙 평가기' 실습에서 deny 규칙이 allow 규칙을 이기는지 확인합니다. 실제 도구에서는 AGENTS.md에 "새 라이브러리를 추가하기 전에 물어볼 것" 한 줄을 넣고 같은 요청을 두 번 보내 차이를 봅니다(연습 화면은 매뉴얼 3).

검증: 받은 코드를 직접 돌려 봅니다

이 절을 읽고 나면 AI가 준 코드를 실행하고 테스트 결과를 읽어 고칠 줄 압니다. Test → Revise → Integrate 구간입니다.

01의 연습 화면에서 AI가 처음 준 코드를 그대로 가져왔습니다. 실행 버튼을 누르고 테스트 탭을 보세요. 세 개 가운데 두 개가 실패합니다. 콘솔의 오류 문장을 읽고 JS 탭에서 한 줄을 고친 뒤 다시 실행합니다.

고친 뒤에는 태그를 '시험'으로 바꿔 보세요. 한 개가 나와야 합니다. 이렇게 직접 눌러 본 것만 "확인했다"고 말합니다.

"돌아가니까 됐다"로 끝내기

첫 화면에서는 멀쩡해 보여도 데이터가 하나 빠지거나 네트워크가 느려지면 깨지는 코드가 많습니다. AI가 준 코드는 적어도 세 가지를 바꿔 보며 돌립니다. 빈 데이터, 빠진 값, 느린 응답. 11주차의 로딩·빈·오류 세 상태가 이 습관의 이름입니다.

수업 과제에서 이렇게: 11주차 알파 버전에서는 데이터 경로 한 곳(fetch 또는 localStorage)을 이런 식으로 직접 확인하고 Network 탭 캡처를 README에 넣습니다(11주차). 12주차에는 checklist.md의 한 줄을 자동 테스트 하나로 옮깁니다(12주차). 검토 질문 6묶음은 AI 코드 검토 체크리스트에 있습니다.

통과하는 리뷰 ≠ 맞는 리뷰: AI 검토의 한계

내부 동작
AI 리뷰어도 같은 종류의 모델입니다. '그럴듯한 코드'를 보고 그럴듯하게 판단합니다. 구현을 그대로 베껴 기대값을 계산하는 테스트는 버그가 있어도 통과합니다. 사용자 입력을 innerHTML에 넣는 코드는 화면에서는 멀쩡해 보이지만 5주차에서 본 것처럼 스크립트가 섞여 들어올 수 있습니다.
명세·문서
MDN · Using the Fetch API(404는 reject되지 않습니다) · 5주차 · AI 코드의 수정과 실행 확인
트레이드오프
테스트를 많이 쓸수록 안전하지만 시간이 듭니다. 이 수업의 기준은 순수 함수(입력 → 출력) 하나에 테스트 하나부터입니다. 화면을 누르는 테스트(E2E)는 선택 모듈입니다.
5분 실험
위 실습의 첫 테스트를 "구현을 베낀 테스트"로 바꿔 봅니다. expect(filterByTag(sample, '수업')).toHaveLength(filterByTag(sample, '수업').length)처럼 기대값을 함수 결과로 계산하면, JS 탭의 includes를 startsWith로 바꿔 틀리게 만들어도 통과합니다. 테스트가 무엇을 확인하는지 읽어야 하는 이유입니다.

"AI가 다 해 줘도 되나요?" — 설명 · 검증 · 판단

이 절을 읽고 나면 불안의 정체가 '누가 썼나'가 아니라 '설명하고 검증하고 판단할 수 있나'라는 것을 알게 됩니다.

5주차 설문에서 여러 분이 같은 질문을 했습니다. "AI가 거의 다 해 주는 느낌이라 이래도 되나 싶다", "AI가 코드 많은 부분을 작성해 이게 맞는지 고민된다". 답은 늘 같은 세 단어입니다.

  1. 설명이 코드가 무엇을, 왜 그렇게 하는지 내 말로 말할 수 있다.
  2. 검증직접 실행하고, 테스트하고, 화면과 Network 탭에서 확인했다.
  3. 판단무엇을 받아들이고 무엇을 뺄지, 어디까지 맡길지 내가 정했다.

세 가지가 되면 AI가 써 준 코드여도 괜찮습니다. 세 가지가 안 되면 내가 손으로 친 코드여도 괜찮지 않습니다. 평가도 이 기준입니다. 이해 · 판단 · 검증 · 협업 · 기록을 보고, 코드의 양이나 어떤 AI를 썼는지는 보지 않습니다.

YOUR CODE, YOUR RESPONSIBILITY

OT의 문장을 그대로 가져옵니다. 제출한 코드에 대해 다음 다섯 가지를 설명할 수 있어야 합니다.

구조
파일이 어떻게 나뉘고 데이터가 어디에 사는지.
동작
입력에서 화면이 바뀌기까지 어떤 순서로 실행되는지.
선택 이유
왜 이 방법인지, 다른 길은 무엇이었는지.
테스트
무엇을 어떻게 확인했는지.
한계·위험
어디서 깨질 수 있는지, 무엇을 아직 모르는지.

팀 스튜디오가 끝날 때마다 'YOUR CODE 1분'을 합니다. 팀원 한 명이 그 주에 AI가 만든 코드나 문서 한 조각을 1분 동안 설명합니다. 설명이 안 되면 그 조각은 아직 우리 코드가 아닙니다. 그때 쓰는 요청 문장이 아래에 있습니다.

언제 AI가 과한가

맡기지 않는 편이 나은 순간도 있습니다. 판단이 우리 것이어야 하거나, 내 눈으로 찾는 연습 자체가 목적이거나, 넣으면 안 되는 정보가 있을 때입니다.

AI에게 맡기지 않는 편이 나은 상황
상황맡기지 않는 이유대신
팀 질문과 사용 장면 고르기 (9주차)판단은 팀의 것입니다. AI는 초안과 빠진 관점까지입니다.쪼개기 표 초안만 맡기고, ★는 사람이 찍습니다.
AI 코드 검토 실습의 첫 단계 (12주차, NO AI)내 눈으로 문제를 찾는 연습이 목적입니다.검토 질문 6묶음으로 먼저 보고, 그다음 AI 리뷰와 비교합니다.
알파 테스트 원본 기록 (13주차, LIMITED)익명화 전 기록에는 개인정보가 섞일 수 있습니다.익명화한 뒤 패턴 정리만 맡깁니다.
개인 회고 (15주차, LIMITED)내용은 내 경험이어야 합니다.맞춤법과 구조 정리만 맡깁니다.
비밀 키 · 계정 정보 · 학생 이름금지선입니다. 학습에 쓰이지 않아도 입력 자체를 하지 않습니다.키는 환경 변수와 서버리스에, 이름은 '팀원 1·2·3'으로.

기준 한 문장: "AI보다 코드를 빨리 쓰는 사람이 아니라, AI에게 일을 잘 맡기고 그 결과를 판단할 수 있는 사람"이 되는 것이 이 수업의 목표입니다. 처음부터 모든 도구를 알 필요는 없습니다.

도구 비교: 이름만 다릅니다

이 절을 읽고 나면 네 도구의 공통 원리를 한 문장으로 말하고, 우리 팀이 어떤 경로로 시작할지 고를 수 있습니다.

채팅형(ChatGPT Edu)이든 코딩 에이전트(Codex, Claude Code, Copilot)든 하는 일은 같습니다. 읽고, 바꾸고, 실행하고, 사람이 확인합니다. 다른 것은 '얼마나 자동으로 하느냐'와 '어디서 멈추고 묻느냐'뿐입니다.

  1. 읽는다지시 파일(AGENTS.md · CLAUDE.md · 프로젝트 지시)과 코드를 먼저 읽습니다.
  2. 바꾼다변경을 제안합니다. 에이전트는 diff(+ − 줄)로 보여 주고, 채팅은 코드 블록으로 줍니다.
  3. 실행한다에이전트는 테스트와 명령을 직접 돌립니다. 채팅은 내가 Live Server에서 돌립니다.
  4. 사람이 확인한다승인하고, 읽고, 되돌립니다. 이 지점을 없애는 설정이 금지선입니다.

'사람이 확인하는 지점'은 도구마다 다른 곳에 있습니다.

ChatGPT Edu
파일을 직접 바꾸지 않습니다. 제안을 내가 읽고 적용합니다. JavaScript는 실행해 주지 않으므로 브라우저(Live Server)에서 직접 확인합니다.
Codex
프리셋 "Ask for approval"에서는 워크스페이스 밖 파일과 네트워크가 필요할 때 묻습니다. 안에서의 편집과 명령은 샌드박스 안에서 바로 합니다.
Claude Code
Manual 모드에서 편집과 명령마다 묻습니다. 최근 버전은 auto 모드로 시작할 수 있어 Shift Tab으로 ⏸ manual mode on을 확인합니다.
GitHub Copilot
agent mode는 기본으로 명령 실행 전에 승인을 받습니다. 요청마다 크레딧을 씁니다.

경로는 셋 중 하나면 됩니다. ChatGPT Edu 웹에 파일을 붙여 넣고 제안을 내가 적용하는 길, Codex를 학교 계정으로 쓰는 길, Claude Code를 쓰는 길. 유료 여부가 성적 차이로 이어지지 않도록 과제는 어느 길로도 할 수 있게 설계되어 있습니다.

학교 ChatGPT Edu 계정으로 Codex 로그인이 되는지, 어떤 모델과 한도가 열려 있는지는 학교 워크스페이스 설정에 달려 있어 수업 직전에 확인해 안내합니다. 로그인이 안 되면 eTL 메시지로 알려 주세요. Codex가 안 되어도 ChatGPT Edu 웹과 Claude Code 경로로 과제를 할 수 있습니다.

해 보기 · 권한 요청 읽고 답하기

에이전트가 멈추고 묻는 순간이 '사람이 확인하는 지점'입니다. 아래 연습 화면에서 요청을 보내고, diff를 읽고, 권한 요청에 번호로 답해 봅니다. 숫자 키 1~4, ↑ ↓, Esc로도 고를 수 있습니다. 문구는 Claude Code 2.1의 Bash 권한 요청 원문을 썼고, 다른 도구도 같은 구조입니다.

수업 과제에서 이렇게: 10주차 팀 과제 '저장소와 하네스'는 AI REQUIRED이고, 세 경로 가운데 하나면 됩니다(10주차). 도구별 자세한 순서는 Claude Code 따라 하기와 Codex 안내의 대응표를 봅니다.

권한 최소화: 규칙은 deny → ask → allow 순서로 읽힙니다

내부 동작
Claude Code의 권한 규칙은 allow · ask · deny 목록으로 설정 파일(.claude/settings.json)에 적습니다. 평가 순서는 deny → ask → allow이고 처음 맞는 규칙이 결정합니다. 문서의 문장: "An allow rule can't carve an exception out of a deny rule." 규칙은 모델이 아니라 프로그램이 강제합니다. 프롬프트나 CLAUDE.md는 모델이 하려는 일을 바꾸지만, 무엇이 허용되는지는 바꾸지 못합니다. Codex는 같은 일을 두 층으로 나눕니다. 샌드박스(어디에 쓸 수 있나, 네트워크가 되나)와 승인 정책(언제 묻나)입니다.
명세·문서
Claude Code · Permissions · Claude Code · Permission modes · Codex · Agent approvals and security
트레이드오프
묻는 횟수를 줄이면 빠르지만, 한 번 잘못 허락한 규칙은 저장소의 다음 세션에도 남습니다(Bash의 "don't ask again"은 .claude/settings.local.json에 저장). deny 규칙은 명령 문자열만 보기 때문에 sh -c '…'처럼 우회한 명령은 막지 못합니다. 진짜 경계가 필요하면 샌드박스나 훅을 씁니다.
5분 실험
아래 실습은 규칙 평가 순서를 흉내 낸 작은 함수입니다. 시작 코드는 allow를 먼저 보는 버그가 있어 git push가 허용됩니다. 순서를 deny → ask → allow로 고치고 테스트를 통과시키세요.

설정 파일 예(공식 문서 원문)입니다. npm run …은 묻지 않고, git push는 사람이 하게 막습니다.

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}

금지선과 AI 4등급

이 절을 읽고 나면 하지 말아야 할 네 가지를 구체적인 장면으로 알고, 과제 카드의 등급 표시를 읽을 수 있습니다.

AI 사용은 기본이지만 선이 있습니다. OT의 금지선 네 가지를 실제 장면으로 옮기면 이렇습니다.

검증 없는 제출
AI가 준 코드를 한 번도 실행하지 않고 올리기. "테스트 통과"라는 AI의 말을 출력도 안 보고 믿기. 02의 실습처럼 직접 돌린 것만 제출합니다.
비밀정보 입력
API 키, 비밀번호, .env 내용, 학생 실명과 연락처를 프롬프트나 저장소에 넣기. ChatGPT Edu가 대화를 기본적으로 모델 학습에 쓰지 않는다는 것과 "넣어도 된다"는 다른 말입니다. 공식 문서상 워크스페이스 관리자는 대화 기록에 접근할 수 있는 구조입니다.
확인 안 한 정보·출처
AI가 알려 준 라이브러리 이름, 수치, 문서 링크를 열어 보지 않고 README나 발표에 쓰기. AI는 틀린 정의와 지어낸 출처를 자신 있게 말할 수 있습니다. 공식 문서를 직접 엽니다.
무조건적 에이전트 권한
--dangerously-skip-permissions(Claude Code), --yolo(Codex)처럼 묻지 않는 모드로 실행하기. 이 플래그는 '사람이 확인하는 지점'을 전부 없앱니다. 수업 노트북에서는 쓰지 않습니다.

평가 기준은 이해 · 판단 · 검증 · 협업 · 기록입니다. 세 가지는 감점입니다. 설명 못 하는 코드, 검토 없는 제출, 출처 미기재. 세부 배점은 eTL 안내를 따릅니다.

확인 문제

Q110주차 팀 과제 '저장소와 하네스'는 AI REQUIRED입니다. 이 등급이 뜻하는 것은?

  • 유료 도구를 전제로 한 과제는 없습니다. 세 경로 중 하나면 됩니다.

  • 맞습니다. REQUIRED는 "AI를 쓰는 것이 과제의 일부"라는 뜻이고, 어떤 도구인지는 팀이 고릅니다.

  • 등급과 관계없이 설명 · 검증 · 판단은 늘 필요합니다.

Q2금지선에 해당하는 것을 모두 고르세요.

  • 비밀정보 입력입니다. 키는 지우거나 YOUR_KEY로 바꾼 뒤 묻습니다.

  • 9주차 'AI와 함께'의 정상적인 사용입니다. 학생 이름은 빼고 올립니다.

  • 검증 없는 제출입니다. 출력을 읽고 테스트가 무엇을 확인하는지 봅니다.

  • 오히려 해야 할 일입니다. 확인 안 한 정보를 쓰는 것이 금지선입니다.

  • 무조건적 에이전트 권한입니다. 사람이 확인하는 지점이 사라집니다.

Q3에이전트가 파일을 바꾸기 전에 보여 주는, +와 - 줄로 된 변경 내용을 무엇이라고 부르나요? (영어 네 글자)

diff입니다. 에이전트의 /diff, 터미널의 git diff, GitHub PR의 Files changed 탭이 모두 같은 것을 보여 줍니다.

Q413주차 수업의 'AI와 함께'(알파 테스트 기록 정리)는 AI LIMITED입니다. 할 수 있는 것은?

  • 익명화 전 원본은 넣지 않습니다. 개인정보가 섞입니다.

  • 맞습니다. LIMITED는 "이 부분만"이라는 뜻이고, 13주차에는 익명화한 뒤 패턴 정리까지입니다.

  • 그것은 NO AI입니다. LIMITED는 허용되는 부분이 과제 카드에 적혀 있습니다.

Q5에이전트가 "테스트 5개 모두 통과했습니다"라고 답했습니다. 다음에 할 일은?

  • AI의 말은 아직 주장입니다. 출력을 읽기 전에는 확인한 것이 아닙니다.

  • 맞습니다. 통과하는 테스트가 맞는 테스트는 아닙니다. 구현을 베낀 테스트는 버그가 있어도 통과합니다.

  • 같은 모델에게 다시 물어도 검증이 되지 않습니다. 내가 출력을 봅니다.

수업 과제에서 이렇게: 매주 과제 카드의 AI 등급 칸을 먼저 봅니다. 12주차 검토 실습(12주차)과 13주차 알파 테스트 정리(13주차)에 등급이 바뀌는 구간이 있습니다.

AI USE NOTE 양식

이 절을 읽고 나면 네 칸짜리 AI USE NOTE를 쓰고, 어디에 두는지 압니다. 15주차 포트폴리오는 이 노트를 모은 것입니다.

AI USE NOTE는 "AI를 썼다"는 고백이 아니라 "무엇을 맡기고 무엇을 내가 판단했는지"의 기록입니다. 네 칸이면 충분합니다. 길게 쓰지 않습니다. 한 칸에 한두 줄입니다.

AI USE NOTE
- 어떤 도구: (ChatGPT Edu · Codex · Claude Code 중 무엇을, 어떤 모드로. 안 썼으면 "없음")
- 어떤 작업을 맡겼나: (초안 · 설명 · 오류 찾기 · 리뷰 · 반복 작업 중 무엇 — 요청 문장을 한 줄로)
- 무엇을 판단했나: (받아들인 것 · 거절한 것 · 바꾼 것과 그 이유)
- 어떻게 검증했나: (직접 실행 · 눌러 봄 · Network 탭 · 테스트 출력 · 다른 사람 리뷰 중 무엇)

PR 본문에는 한 줄로 줄여 씁니다. AI USE NOTE: 도구 / 맡긴 작업 / 판단 / 검증. 채워 보면 이렇습니다. 02 실습의 상황입니다.

AI USE NOTE
- 어떤 도구: ChatGPT
- 어떤 작업을 맡겼나: 코드 작성
- 무엇을 판단했나: 없음
- 어떻게 검증했나: 잘 됨
AI USE NOTE
- 어떤 도구: ChatGPT Edu (Chat, 기본 모델)
- 어떤 작업을 맡겼나: 태그로 메모를 거르는 filterByTag 초안.
  "함수 하나, 라이브러리 없이, 확인 방법까지" 요청
- 무엇을 판단했나: 태그 없는 메모에서 TypeError가 나는 것을
  찾아 다시 요청. (n.tags ?? [])로 고친 버전을 채택
- 어떻게 검증했나: 실습 테스트 3개 통과, 태그를 바꿔 가며
  화면 확인. 빈 배열일 때 "0개" 표시까지 눌러 봄
어디에 두나
PR마다 본문에 한 줄, 팀 제출마다 README의 AI USE NOTE 표(영향이 큰 것 2~5개), 개인 과제는 README의 'AI USE NOTE' 절. 15주차 개인 포트폴리오(docs/portfolio-이름.md)는 한 학기 노트를 모은 것입니다. 양식 파일은 교안 저장소의 templates/AI-USE-NOTE.md에 있고 10주차에 하네스 문서와 함께 복사합니다.
대화 링크
ChatGPT Edu의 공유 링크는 같은 학교 워크스페이스 구성원만 열 수 있고, 학교 설정에 따라 공유 자체가 꺼져 있을 수 있습니다. 링크가 안 되면 요청 문장과 핵심 답을 짧게 옮겨 적거나 캡처를 README에 넣습니다. 에이전트는 /export로 대화를 파일로 남길 수 있습니다.
쓰지 않는 것
학생 실명, 비밀 키, 내부 링크. 공개 저장소입니다.
